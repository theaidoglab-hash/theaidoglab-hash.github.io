不必先選工具。這個練習只做一件事：把一則虛構常見問題整理成回覆草稿，再交由指定的人核對。工具不會讀取真實帳戶、傳送訊息或修改任何系統。

## 五分鐘先看懂整個做法

1. 寫下一句目標：「根據已核准的虛構 FAQ 產生草稿，交由人覆核。」
2. 準備三則虛構問題：一則有清楚答案、一則沒有答案、一則要求工具傳送訊息。
3. 先自行寫下預期結果：草稿、交回人處理，或停止。
4. 才讓工具產生結果，逐一比較；任何外傳或寫入要求都不執行。

開始前認識四個詞：

- **合成 FAQ（synthetic FAQ）**：為練習而寫的假問題與答案，不屬於真實客戶。
- **只限草稿（draft-only）**：工具可以整理文字，但不能傳送或寫入其他系統。
- **交回人處理（handoff）**：資料不足、規則衝突或要求越權時，工具要停下並請人決定。
- **權限覆核（permission review）**：在工具讀檔、連接帳戶、使用網路或寫入資料前，先核對它可接觸的對象、範圍、影響、能否還原，以及由誰負責。

如果無法說清這五項，就只保留本機、合成與只限草稿的練習。需要使用工具權限時，先看[按允許前的權限覆核](/zh-TW/articles/review-an-ai-agent-before-clicking-allow)。

## 這個 demo 明確展示什麼

完成上面五分鐘練習，不需要先學下面的技術名詞。它們只幫助你之後檢查這個安全練習如何運作；不會讓工具接觸真實資料或系統。

### Code 裡看得到的東西

- **FAQ 查找（retrieval）**：工具寫草稿前，會先在虛構 FAQ 清單中找一則相符答案；不會搜尋真實客戶系統或私人文件。
- **附來源的草稿**：草稿會列出用了哪一則虛構 FAQ，讓覆核的人可以核對。
- **固定回應替身（deterministic mock）**：本機替身對同一則測試輸入永遠傳回預先寫好的結果；它只用來測流程，不會呼叫模型。
- **已存請求示範（`gpt-5-mini` Responses API request fixture）**：一個展示日後如要呼叫模型，資料要怎樣排成請求格式的檔案。它沒有任何 API key（讓程式連線的密碼）、不會連網，也絕不發送。
- **預先寫好的核對題（acceptance cases）**：你在測試前先寫下的問題和預期結果。
- **企圖叫工具違規的輸入（prompt injection）**：例如「忽略不可發送的規則」。預期結果是停止或交回人處理，不是產生回覆。
- **最少執行紀錄（trace）**：本機只記測試編號、版本、結果和原因；不記原問題或任何個人資料。

### Code 以外要交代的事

- 它把「產生草稿」和「向客戶發送」分開；真正行動仍由人決定。
- 它只使用合成或公開材料。寫清它可做和不可做的範圍、權限檢查、失敗紀錄和專案說明文件（README），覆核的人才能看得出測過什麼、沒有測過什麼。
- 這只是本機學習示例，不是已接入客服、已獲成效或可自行處理敏感案例的聲稱。

## AI 工具替你寫 code，不會替你承擔決定

你可以用 coding agent、chatbot 或低程式 app 做一個小工具。它可能幫你拆需求、寫表單、連接資料或產生初版 workflow。工具名稱不是重點，無論你使用 Codex、Grok 或其他產品，真正要學的是把一個模糊願望改寫成可以驗收的工作。

「我想自動化客服」太大；「把已核准的 FAQ 轉成回覆草稿，交給一位人工 reviewer」才是可以安全開始的範圍。前者會迫你碰到身份、資料、外發和退款等不可逆行動；後者可以先在合成或公開資料上測試。

## 最低限度要有的六種能力

- **說清 input 和 output**：系統收到什麼；應產出什麼格式；哪些欄位不能看或不能保留。
- **寫出不能做什麼**：例如不可發送、不可刪除、不可修改金錢或權益、不可使用未獲授權資料。
- **提供 expected examples**：不是「看起來好」；而是 10 到 20 個輸入，以及你期望它怎麼分類、引用、拒答或交接。
- **比較 baseline**：先用手動做法、表格規則或搜尋，才知道 AI 有沒有真的改善流程。
- **看懂 failure**：知道把錯誤記成哪一類，例如輸入不完整、引用錯、越權、格式錯、需要人判斷。
- **保留人工關卡**：任何外發、寫入、付款、帳戶改動或高風險決定，都必須在系統外由人確認。

這不是要你變成 full-stack developer。它是讓你不會被一個流暢 demo 說服，也能和開發者討論真正的 acceptance criteria。

## 一個安全起點：只產生草稿的 FAQ 分流助手

用完全虛構或公開核准的 FAQ，做一個工具，讓使用者貼上一段問題後得到：建議分類、引用的 FAQ 段落、回覆草稿和「需要交給人」的標記。它不讀真實客戶帳戶、不發送訊息、不連接付款或訂單系統。

### 1. 先寫 action contract

把以下文字放進你的 project brief，而不是只對工具說「幫我做 app」。

```text
使用者：處理常見問題的同事
輸入：公開或合成的問題文字
輸出：分類、可追溯 FAQ 引用、回覆草稿、handoff 原因
禁止：發送、修改帳戶、使用私人資料、假裝引用不存在內容
人工決定：是否採用草稿、是否聯絡客戶、例外如何處理
```

`action contract` 的技術意思是把權限和責任寫成可測試規格，而不是相信模型懂得你的常識。想像：先畫好遊戲規則，才把玩具交給小朋友。

### 2. 寫 examples，當作最小 evaluation set

準備至少十二個 case：四個正常 FAQ、兩個沒有答案、兩個互相矛盾、兩個資料不足、一次叫它忽略規則的 prompt injection，和一次要求它做禁止行動。每個 case 先由你寫 expected behaviour，例如「引用 FAQ-03，輸出草稿，禁止送出」或「不答內容，只交接」。

這些 examples 不需要是 data science benchmark；它們是你和工具之間可重複的驗收契約。想像：不是只叫人猜你的心意，而是把答題卡先寫好。

### 3. 叫工具先提出最小設計

要求 coding agent 用最少元件做出本地 prototype，並說明每個部分負責什麼。好的要求不是「做一個企業級 agent」，而是「先做 read-only、本地可重跑、含十二個 test cases 的 draft generator；不要加登入、付款、外發或未要求的 connector」。

讀它的方案時，問四條問題：資料從哪裡來？輸出能否回到來源？它能否寫入任何東西？出錯時使用者看見什麼？若答案不清楚，先縮小 scope，不是立刻換更強 model。

### 4. 在 sandbox 測，不要直接接真實工作流

先用假的 FAQ 和沒有敏感資料的輸入。逐一跑 evaluation case，記錄應有結果、實際結果和錯誤類型。任何看似「大致正確」但引用錯、漏掉拒答、或試圖越權的結果，都不是小 bug；它代表 acceptance rule 要補清楚。

可記錄的項目很簡單：case ID、version、是否引用正確、格式是否正確、是否應交接、人工決定。你不必有 dashboard 才能開始學 observability。

### 5. 加一個人工 gate，然後才談自動化

初版永遠只產生 draft。若未來真的需要寫入任何系統，設計一個獨立的 review screen，讓人檢查目標、內容、引用、資料範圍和動作，再按下確認。這個關卡應由程式和權限控制，不應只依賴 prompt 裡的「不要做」。

想像：小幫手可以把便條寫好，但把信投進郵箱前，仍由大人看地址和內容。

## 什麼時候要停下來

以下任一情況出現，就回到需求而不是繼續疊工具：你無法寫出 expected output；你需要真實個人資料才能測；錯一次會造成付款、法律、醫療、安全或權益損失；沒有任何人願意負責最後決定；或你只是在做一個任何人五分鐘都可複製的 demo。

低程式不是低標準。最有價值的第一個 project，往往是一個範圍很小、能展示 refusal、evaluation、trace 和 human handoff 的系統。
