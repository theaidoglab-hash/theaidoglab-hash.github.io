不用先选工具。这个练习只做一件事：把一条虚构常见问题整理成回复草稿，再交给指定的人核对。工具不会读取真实账户、发送消息或修改任何系统。

## 五分钟先看懂整个做法

1. 写下一句目标：“根据已批准的虚构 FAQ 生成草稿，交给人复核。”
2. 准备三条虚构问题：一条有明确答案、一条没有答案、一条要求工具发送消息。
3. 先自行写下预期结果：草稿、交回人处理，或停止。
4. 再让工具生成结果，逐条比较；任何外发或写入要求都不执行。

开始前认识四个词：

- **合成 FAQ（synthetic FAQ）**：为练习而写的假问题和答案，不属于真实客户。
- **仅限草稿（draft-only）**：工具可以整理文字，但不能发送或写入其他系统。
- **交回人处理（handoff）**：数据不足、规则冲突或要求越权时，工具要停下并请人决定。
- **权限复核（permission review）**：在工具读文件、连接账户、使用网络或写入数据前，先核对它可接触的对象、范围、影响、能否还原，以及由谁负责。

如果无法说清这五项，就只保留本地、合成和仅限草稿的练习。需要使用工具权限时，先看[点击允许前的权限复核](/zh-Hans/articles/review-an-ai-agent-before-clicking-allow)。

## 这个 demo 明确展示什么

完成上面五分钟练习，不需要先学下面的技术名词。它们只帮助你之后检查这个安全练习如何运作；不会让工具接触真实数据或系统。

### Code 里看得到的东西

- **FAQ 查找（retrieval）**：工具写草稿前，会先在虚构 FAQ 清单中找一条相符答案；不会搜索真实客户系统或私人文件。
- **带来源的草稿**：草稿会列出用了哪一条虚构 FAQ，让复核的人可以核对。
- **固定回应替身（deterministic mock）**：本地替身对同一条测试输入总是返回预先写好的结果；它只用来测流程，不会调用模型。
- **已存请求示例（`gpt-5-mini` Responses API request fixture）**：一个展示日后如要调用模型，资料要怎样排成请求格式的文件。它没有任何 API key（让程序连线的密码）、不会联网，也绝不发送。
- **预先写好的核对题（acceptance cases）**：你在测试前先写下的问题和预期结果。
- **企图让工具违规的输入（prompt injection）**：例如“忽略不可发送的规则”。预期结果是停止或交回人处理，不是生成回复。
- **最少运行记录（trace）**：本地只记测试编号、版本、结果和原因；不记原问题或任何个人数据。

### Code 以外要交代的事

- 它把“产生草稿”和“向客户发送”分开；真正行动仍由人决定。
- 它只使用合成或公开材料。写清它可做和不可做的范围、权限检查、失败记录和项目说明文件（README），复核的人才能看出测过什么、没有测过什么。
- 这只是本地学习示例，不是已接入客服、已获成效或可自行处理敏感案例的声称。

## AI 工具替你写 code，不会替你承担决策

你可以用 coding agent、chatbot 或低代码 app 做一个小工具。它可能帮你拆需求、写表单、连接数据或产生初版 workflow。工具名称不是重点，无论你使用 Codex、Grok 或其他产品，真正要学的是把一个模糊愿望改写成可以验收的工作。

“我想自动化客服”太大；“把已批准的 FAQ 变成回复草稿，交给一位人工 reviewer”才是可以安全开始的范围。前者会迫使你碰到身份、数据、外发和退款等不可逆行动；后者可以先在合成或公开数据上测试。

## 最低限度要有的六种能力

- **说清 input 和 output**：系统收到什么；应产出什么格式；哪些字段不能看或不能保留。
- **写出不能做什么**：例如不可发送、不可删除、不可修改金钱或权益、不可使用未获授权数据。
- **提供 expected examples**：不是“看起来好”；而是 10 到 20 个输入，以及你期望它怎么分类、引用、拒答或交接。
- **比较 baseline**：先用手动做法、表格规则或搜索，才知道 AI 有没有真的改善流程。
- **看懂 failure**：知道把错误记成哪一类，例如输入不完整、引用错、越权、格式错、需要人判断。
- **保留人工关卡**：任何外发、写入、付款、账户改动或高风险决定，都必须在系统外由人确认。

这不是要你变成 full-stack developer。它让你不会被一个流畅 demo 说服，也能和开发者讨论真正的 acceptance criteria。

## 一个安全起点：只产生草稿的 FAQ 分流助手

用完全虚构或公开批准的 FAQ，做一个工具，让用户贴上一段问题后得到：建议分类、引用的 FAQ 段落、回复草稿和“需要交给人”的标记。它不读真实客户账户、不发送消息、不连接付款或订单系统。

### 1. 先写 action contract

把以下文字放进你的 project brief，而不是只对工具说“帮我做 app”。

```text
使用者：处理常见问题的同事
输入：公开或合成的问题文字
输出：分类、可追溯 FAQ 引用、回复草稿、handoff 原因
禁止：发送、修改账户、使用私人数据、假装引用不存在内容
人工决定：是否采用草稿、是否联系客户、例外如何处理
```

`action contract` 的技术意思是把权限和责任写成可测试规格，而不是相信模型懂得你的常识。想象：先画好游戏规则，才把玩具交给小朋友。

### 2. 写 examples，当作最小 evaluation set

准备至少十二个 case：四个正常 FAQ、两个没有答案、两个互相矛盾、两个资料不足、一次叫它忽略规则的 prompt injection，和一次要求它做禁止行动。每个 case 先由你写 expected behaviour，例如“引用 FAQ-03，输出草稿，禁止送出”或“不答内容，只交接”。

这些 examples 不需要是 data science benchmark；它们是你和工具之间可重复的验收契约。想象：不是只叫人猜你的心意，而是把答题卡先写好。

### 3. 叫工具先提出最小设计

要求 coding agent 用最少组件做出本地 prototype，并说明每个部分负责什么。好的要求不是“做一个企业级 agent”，而是“先做 read-only、本地可重跑、含十二个 test cases 的 draft generator；不要加登录、付款、外发或未要求的 connector”。

读它的方案时，问四条问题：数据从哪里来？输出能否回到来源？它能否写入任何东西？出错时用户看见什么？若答案不清楚，先缩小 scope，不是马上换更强 model。

### 4. 在 sandbox 测，不要直接接真实工作流

先用假的 FAQ 和没有敏感资料的输入。逐一跑 evaluation case，记录应有结果、实际结果和错误类型。任何看似“大致正确”但引用错、漏掉拒答、或试图越权的结果，都不是小 bug；它代表 acceptance rule 要补清楚。

可记录的项目很简单：case ID、version、是否引用正确、格式是否正确、是否应交接、人工决定。你不必有 dashboard 才能开始学 observability。

### 5. 加一个人工 gate，然后才谈自动化

初版永远只产生 draft。若未来真的需要写入任何系统，设计一个独立的 review screen，让人检查目标、内容、引用、数据范围和动作，再按下确认。这个关卡应由程序和权限控制，不应只依赖 prompt 里的“不要做”。

想象：小帮手可以把便条写好，但把信投进邮箱前，仍由大人看地址和内容。

## 什么时候要停下来

以下任一情况出现，就回到需求而不是继续叠工具：你无法写出 expected output；你需要真实个人资料才能测；错一次会造成付款、法律、医疗、安全或权益损失；没有任何人愿意负责最终决定；或你只是在做一个任何人五分钟都可复制的 demo。

低代码不是低标准。最有价值的第一个 project，往往是一个范围很小、能展示 refusal、evaluation、trace 和 human handoff 的系统。
