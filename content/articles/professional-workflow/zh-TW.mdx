> 一個 workflow 值不值得信，取決於 reviewer 能否跟到需求、測試、失敗與決策；不是 AI 寫了多少 code。

## 從模糊要求開始
假設有人說：「增加一個 AI 功能，協助使用者草擬客戶回覆。」先不要問要用哪個模型。要先問輸入來自哪裡、誰可以讀取、輸出只是 draft 還是可以寄出、哪些情況必須交由人工處理、如何判斷內容可接受，以及錯誤會造成什麼後果。

## 把要求寫成 spec
定義輸入、輸出、不可做的事和 acceptance criteria。例如：系統只讀取已核准的合成 ticket；輸出必須標示為 draft；缺少訂單資料時不得自行補作；任何寄送動作不在 scope；測試集中的敏感資料不得出現在 log。

## 拆成可驗收 tickets
將工作分成資料 schema、rule validation、draft generation、evaluation、audit record 和 UI review。每個 ticket 都要有明確完成條件。這樣 AI coding assistant 只處理目前的邊界，而不是一次猜完整個產品。

## Tests 是 feedback loop
先建立 deterministic rules 和固定 cases，再測試模型輸出。測試正常情況，也測 missing field、malicious instruction、timeout、duplicate request 和 retry。付款或外部寫入類工作還要考慮 idempotency；本例則明確維持 draft-only。

## Debugging 與 review
失敗時保存輸入類型、版本、rule result、模型狀態和人工決策，不保存不必要的原始個人資料。修正後重跑相同 cases，避免只測剛才失敗的一例。Code review 不只看 syntax，也要檢查權限、error path、logging、rollback，以及使用者是否知道輸出仍待審核。

## 把 acceptance contract 寫成一頁

用前面完全虛構的 reply-drafting feature 做例子，以下表格已足夠，不必讓 coding task 漂成一句「做一個 AI assistant」。

| 工作部分 | 寫 code 前要定的決策 | 別人可以執行的檢查 | 刻意不做什麼 |
| --- | --- | --- | --- |
| Input | 只讀提供的 synthetic ticket。 | 空 ticket 或未知 category 要 reject。 | 不碰真實 inbox、CRM 或 attachment。 |
| Draft | 提議一段清楚標記 `DRAFT` 的回覆。 | 必填欄位要齊；沒有根據就 `HANDOFF`。 | 沒有 send button，也沒有背景發送。 |
| Record | 留下 case ID、version、route 與 reviewer result。 | 用 fixture ID 可以重跑一個失敗 case。 | 不保存 ticket body 或個人資料。 |
| Release | 有名字的 reviewer 接受一個本機 demo。 | Hard-gate case 全過，普通 case 也沒有 regression。 | 不聲稱 production 或客戶成果。 |

在請 coding agent 開始 build 前，先寫 acceptance test。一個好的 request 會是：「加入 schema validator 與列明的五個 case；不要加入 login、network call、database 或 external-send path。」這樣 reviewer 才有一個有限的 diff 可以查看，也有實際理由拒絕 scope expansion。

## 第一次 review 可以正確停在 STOP

假設 agent 提議一個「方便」功能：send 失敗就悄悄 retry，同時儲存完整 ticket 方便重建 draft。兩項都超出原本界線。正確 review result 是 `STOP`，不是「先 merge，之後再修」。保留被拒的 diff 或短 decision note；它證明你能在需求改變前辨認出來。

成功 demo 也一樣。如果只有一段 happy-path screen recording，就標記 `REVISE`，要求補 fixed case、failure route 與 permission review。團隊不需要每張 ticket 第一次就 pass；需要的是清楚說出哪些工作不應該繼續。

## 依 reviewer 要看的次序放 artefact

從 `problem-brief.md` 開始，接著是小型 spec 與 test matrix。再放 implementation diff、一個失敗 case 的 trace 或 error record，以及一段 decision note。Reviewer 應能不讀完每個 source file 也跟到決策。這個次序也讓你在面試解釋 portfolio 時清楚許多。

## 可放進作品集的證據
展示 spec、ticket breakdown、test matrix、一次具體 failure、修正前後差異和 ADR。不要聲稱「production ready」；準確說明哪些環節已驗證、哪些仍使用 mock、哪些操作被刻意禁止。
