When a coding agent says “done”, decide what evidence you need before you keep its first version: a plan, test output, a diff and an open-risk note. If one of those is missing or exceeds the brief, pause the work; this demo stays local, synthetic and draft-only.

## What this Approval Queue demo explicitly demonstrates

### What you can inspect in the build

- A small workflow that reads local FAQs, produces cited drafts and rejects unauthorised actions, with fixed acceptance cases for each route.
- Plans, diffs, test commands, sandbox and permission checks, and traces that make a coding agent’s change reviewable engineering evidence.

### What has to work around the build

- The point is not that an agent replaces a person; it is how a non-developer can review a reversible, draft-only delivery.
- The reviewer’s PASS, REVISE or STOP decision, synthetic-data boundary and absence of external action stay in a local evidence folder first. Move a public-safe version to GitHub only after its owner has reviewed and approved that release.

## A long prompt is still not an acceptable project

“Build me an AI app” can produce a polished screen, several components and plausible copy. It tells you very little about what data was touched, which connector was added, or where a bad output would go. This is where many AI-slop portfolios begin: there is a demo, but no record of the decisions or the failure path.

Codex, Grok and other coding agents have different interfaces, permissions and defaults. Treat the agent as a collaborator that can propose and implement work. You remain accountable for the scope, the acceptable outcome and the final decision.

This guide reuses the Approval Queue in Build Lab. It uses synthetic FAQ material to make a cited reply draft. It cannot send a message, read an account, change data or touch a real customer. The deliberately small case teaches a rerunnable evidence chain; it does not pretend to be a deployed product.

## Six places to pause

### 1. Define one reversible outcome

Reduce “automate customer support” to “classify a synthetic question, cite a synthetic FAQ record and produce a draft for a reviewer.” State what is out of scope: no login, network, personal data retention, outbound message or system write.

That brief becomes the ruler for deciding whether the agent has crossed a boundary. If you cannot state the first output clearly, you cannot yet say how it would be wrong.

### 2. Review a plan before allowing a feature

The agent's first answer should contain only:

- its understanding of the user, input, output and non-goal;
- the files it proposes to create or change;
- each file's responsibility;
- the test command it expects to run;
- assumptions that need your answer;
- data, network and write actions it will not touch.

This is a plan review. Picture it: look at the pieces a child plans to use before letting them build. You do not need to understand every line of code to ask why a local draft tool suddenly needs an API key or database.

## Put acceptance cases ahead of the feature

Write three to five cases that can clearly pass or fail. Each needs an input, an expected route, an expected citation and a prohibited action.

- A supported FAQ should produce a draft, cite the right FAQ ID and ask for human confirmation.
- Missing support should not invent an answer; it should hand off.
- Conflicting instructions should not turn unapproved material into a source.
- A prompt injection attempt should stop and hand off.
- A request to send email or issue a refund should be blocked without an external action.

OpenAI's agent-evaluation guidance treats wrong tool choice, rule violations and workflow regressions as behaviour worth checking. Fixed cases let you compare the same results after each change instead of judging one fluent output. The [official evaluation guide](https://developers.openai.com/api/docs/guides/agent-evals) describes OpenAI workflow tools; this guide only adopts the repeatable-comparison habit. It does not claim that every coding agent creates evals for you.

## Six terms you should be able to inspect

**Plan** is the task list before a change. It shows where the agent expects to work.

**Acceptance test** is a prewritten answer key. It replaces “looks fine” with inputs and expected outcomes.

**Diff** is a comparison of changed code. You may not judge every line, but you can ask whether a new file exceeds the brief or quietly adds login, payment, network access or a database.

**Sandbox** limits what a tool can touch. It can reduce accidents, but it does not decide data rights or business responsibility. Codex describes sandboxing and approvals as configuration-dependent layers, not a portable promise across tools. See the [Codex approvals and security guide](https://learn.chatgpt.com/docs/agent-approvals-security).

**Permission** is the actual ability to read, write or send. A project rule or prompt is not permission control. Stop when a tool asks for files outside the workspace, a real account, an API key or a connector.

**Reviewer decision** records PASS, REVISE or STOP with a reason. It turns “I think it is okay” into a decision another person can inspect.

## Ask for a short handoff after the first build

After the agent completes one thin slice, ask it to return:

- the files actually added or changed;
- the synthetic inputs used;
- expected and actual results for every acceptance case;
- the test command and its status;
- anything it did not test;
- known failures, data limits and claims it cannot make;
- external actions it did not perform.

“Tests passed” is not enough. You should be able to open the result and see how a normal case, an abstention case and an overreach case travelled through the workflow. OpenAI separates automated guardrails from human review: checks can validate input, output or tool behaviour, while sensitive side effects should pause for a person to approve. That [guardrail and human-review guidance](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) is an SDK pattern, not a default for every tool, which is why this case stays draft-only.

## PASS, REVISE and STOP are not grades

PASS means only that this version passed the current cases inside the documented synthetic and local boundary. It is not ready to connect to a real workflow.

REVISE means you found a specific gap: an unstable citation ID, a vague handoff reason or a missing input category. Fix one gap, then rerun the same cases.

STOP means the scope is unsafe or unclear: it needs real data, a write action, a named owner, a definition of error, or a plan that exceeds the original reversible exercise. Stopping is a sound engineering decision.

## When a public GitHub repository is appropriate

Do not invent a repository link before there is an approved public release. Keep the following evidence locally while it is still being reviewed. Once the owner has confirmed that it is safe to publish, a strong portfolio repository does not rely on a model name or a UI screenshot; it retains artefacts a reviewer can actually read:

- a README with the business problem, user, measurable success condition and non-goal;
- the brief and plan, including what the agent was asked not to do;
- synthetic data and the data boundary;
- acceptance cases, a test command and observed results;
- a change review explaining what changed and why it was accepted or rejected;
- failures and the next risk that is still open;
- an honest statement that the work is a local, synthetic, human-reviewed reference, not a production outcome.

These artefacts give an interviewer something real to ask about: requirements, evaluation, permissions and collaboration judgement. They do not guarantee an AI Engineer role, and they do not make every agent-generated line your original work.
