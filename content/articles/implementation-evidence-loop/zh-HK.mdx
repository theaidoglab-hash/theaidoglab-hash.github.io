「我用 coding agent 做咗個 app，run 到」唔係一個可以交代的實作答案。interviewer 或 reviewer 下一步會問：佢原本應該做乜？邊啲 input 唔可以接受？改咗邊一部分？測試證明咗咩？如果錯咗點樣停？

## 用一個細小 feature 練 implementation judgment

想像一個完全合成的 policy-draft tool。user 輸入一條問題，系統只可在已批准文件內選 source，然後輸出 JSON draft 或 `HANDOFF`。它不讀真實帳戶、不發訊息、不改記錄。

先寫 **input contract**：問題必須是 text、document scope 要存在、最大長度是多少、哪些欄位不會接受。再寫 **output contract**：`draft` 必須有 citation IDs；找不到足夠支持時必須是 `HANDOFF`；不得有外發 action。contract 把「看似正常」變成可以測的條件。

## 正常 case 不夠

一組 fixed cases 最少包括：有足夠支持的問題、無支持的問題、過期文件、跨區文件、空 input、錯誤 JSON、prompt injection 字樣，以及 model response timeout。每個 case 寫 expected terminal state，不是只寫「應該 work」。

**Unit test** 檢查小函數或 validator；**integration test** 檢查 source selection、model-shaped fixture 和 output parser 是否一起遵守 contract；**acceptance case** 則由使用者決定回看：這份草稿能否給 reviewer 看，還是要 handoff。三者不能互相取代。

## Coding agent 的位置

coding agent 可以提出 plan、diff 和 tests，但不可以偷偷擴大 scope。reviewer 要看：

- diff 是否加入 login、network、database 或寫入權限，而 brief 沒有要求？
- negative cases 有冇真係 fail，還是只測 happy path？
- input/output schema 有冇在邊界檢查，而唔係希望 prompt 自己守規矩？
- 失敗後系統會不會留 trace、停在 handoff，還是靜靜重試到出現另一個結果？

## 交付證據不等於 production claim

保留 `SPEC.md`、一頁 plan、可讀 diff、test matrix、一次失敗例子、decision record 和 README rerun steps。它們可以展示你如何把要求變成可驗收 feature；不代表你已在真實公司部署、處理客戶資料或帶來業務成效。

若改動牽涉帳戶、付款、外發、醫療、法律或個人資料，縮細成 synthetic、draft-only prototype。沒有人能說清誰批准最後行動時，正確的 implementation decision 是停低，不是加更多 agent。
