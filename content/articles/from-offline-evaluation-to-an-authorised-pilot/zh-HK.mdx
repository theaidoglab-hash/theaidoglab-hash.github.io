> 固定評估集只告訴你 candidate 在那些 case 做成怎樣。想知道個 workflow 有冇幫到團隊，還要先約好誰看結果、跟誰比較，以及何時停止。

## 一個本地 demo 做得好之後，真正欠甚麼？

假設你的 Renewal Triage project 已有 data contract、baseline、固定 holdout、CI check 和 rollback note。你亦能解釋，為何 candidate 的 generic ranking metric 較高，卻仍然要被 gate 擋住。這已經比只有一個 F1 的 notebook 好很多。

但面試官再問一句：「你怎樣知道它幫到 business？」

一個答啱一半嘅回答係：「我會 monitor accuracy 和 reviewer acceptance。」兩者都值得量度，但都不是 business outcome。acceptance 只可反映 reviewer 覺得 queue 是否看得明；accuracy 只可反映 model 是否配合某個 label。它們不能證明 retention、cost、quality 或 customer outcome 因為這個 workflow 而改變。

較完整的答案是：「我會先把四類證據分開，用不會改變任何下游狀態的 shadow review 比較 candidate 和 baseline；只有 data owner、operations owner 和 comparison method 都獲授權後，才定義 business-outcome 問題。」以下是把這個判斷做成可檢查作品證據的方法，而且毋須接駁真實系統。

## 四個數字，不能混成一句『有價值』

| 證據層 | 要問甚麼 | 可以支持甚麼 | 單靠它不可以支持甚麼 |
| --- | --- | --- | --- |
| Hard gate | 有沒有禁止欄位、缺 trace 或 external-action path？ | 本地 build 應停止。 | workflow 有 business value。 |
| Model／route metric | candidate 有沒有正確處理固定 holdout route？ | 該 dataset 上的技術比較。 | team 快咗、customer outcome 改善咗。 |
| Workflow metric | reviewer 可否在既定時間內按 pre-registered checklist 完成 packet？ | 一項受限的 operation observation。 | revenue、retention、滿意度或因果效果。 |
| Delayed business outcome | 經授權的 comparison 在 outcome window 後有沒有看到改變？ | 一個有範圍的 outcome finding。 | 永遠或所有情況都有效。 |

Google 的 ML engineering 指引值得參考，因為它把 metric 和 instrumentation 視為系統的一部分，而不是 model 完成後才補上的裝飾；它亦分開直接可觀察的 objective 和較廣闊的 system health。[Rules of Machine Learning](https://developers.google.com/machine-learning/guides/rules-of-ml) 作品集尤其要守住這個分別：不要把本地 proxy 寫成從未量度過的 outcome。

想像：有個小幫手幫老師把練習卡放進盒。你可以檢查它有沒有放對卡，老師看不看得明標籤；但未可以話它令全部小朋友學得更好，除非你小心比較過後來真正發生的事。

## 先畫 state map，才談 action

```text
PLANNING_ONLY
  -> SHADOW_REVIEW
  -> OWNER_APPROVED_PILOT
  -> OUTCOME_OBSERVATION
  -> HOLD 或 ROLLBACK
```

`PLANNING_ONLY` 是把問題、metric 和邊界寫清楚的階段，甚麼都未接駁。`SHADOW_REVIEW` 是讓 candidate 在 baseline 旁邊只產生 draft queue，再由人用 frozen checklist 比較；它不可以改 account、price、message 或任何決定。

`OWNER_APPROVED_PILOT` 不是 test pass 後自己加上的勳章。它要有資料和 workflow 的 owner、固定 comparison design、人手 reviewer 和 stop path。Renewal Triage 的本地 sidecar 只會**模擬**這個狀態：code 檢查設計是否齊備，同時一直保留 `deployable: false`、沒有 connection 和沒有 automatic action。它不是任何真實機構的批准。

`OUTCOME_OBSERVATION` 只會在另一個已授權的團隊決定收集 outcome 後才開始。很多 outcome 要等數日甚至數月才知道。在 observation window 和 comparison 完成前，狀態應是 `NOT_OBSERVED`，不是「應該有正面效果」。`HOLD` 和 `ROLLBACK` 都是合理結果：一旦有 safety breach、protocol change 或 gate fail，應停 candidate，而不是用「好有韌性」的故事掩飾。

## 未看結果前，先寫九格 pilot contract

在虛構 review-queue 情境中，建立一份 versioned record，至少有以下九格：

1. **Data owner 和 boundary：** 哪一類資料可用、哪些不可用、approval scope、retention expiry 和 deletion owner。技術上方便的資料，若未獲授權，就不是 pilot input。
2. **Operations owner 和 human reviewer：** 誰擁有 workflow，誰可以看、hold 或拒絕 recommendation。model 不是 decision owner。
3. **Frozen comparison：** baseline version、candidate version、assignment unit、comparison strategy 和 protocol 被鎖定的時間。看過靚結果後不可改 threshold、label 或 denominator。
4. **Primary workflow metric：** 定義與受限工作相符的短期量度，例如在指定 review window 內按 checklist 完成 packet 的比例；要寫清 denominator 和 claim boundary。
5. **Safety guardrail：** 設一個不可談判的量度，例如 external-action breach 必須為零，並寫明 fail 時怎樣處理。平均分再好也補救不了不應出現的 action。
6. **Delayed outcome definition：** 寫 outcome、observation window、comparison method，以及它目前為何未觀察到。queue ranking 本身不是 intervention；由人作出的下游 action 要有另一份 policy。
7. **Reviewer evidence：** 規定 reviewer 記錄 route、reason-code reconstruction、missing evidence、checklist result 和 unresolved issue；不要跟 outcome label 混為一談。
8. **Rollback decision：** 甚麼情況要 hold candidate、哪個 baseline 可以留下、誰可重開，以及需要甚麼新 evidence。
9. **Claim statement：** 本地設計真正在示範甚麼、絕不示範甚麼，防止 README 後來變成杜撰 ROI。

### 系統部分，同使用前要講清嘅事

| 系統做法與檢查 | 使用前要講清嘅事 |
| --- | --- |
| Versioned data、feature、model、prompt、baseline 和 evaluation identifiers。 | Decision owner、data owner、operations owner 和 human reviewer。 |
| Fixed cases、frozen comparison protocol、trace、failure record 和 deterministic test。 | Allowed-data boundary、retention、error cost、reviewer capacity 和 intervention authority。 |
| 一個會拒絕 connected 或 action-enabled design 的 static gate。 | Primary workflow measure、safety guardrail、delayed-outcome definition 和 stop rule。 |
| 永遠 draft-only、可逆的 route。 | 對 hold、rollback 或仍缺證據的書面決定。 |

只得其中一邊，project 都會以不同方式不完整。只有 code，不能證明你有權行動；只有 business story，又不能證明聲稱的機制有被比較過。

## 用 Renewal Triage sidecar 練習

[Renewal Triage Lab](/zh-HK/articles/renewal-triage-mlops) 現在有一個小型 local pilot-readiness sidecar。它的 default synthetic design 會被 blocked，因為未有 owner、data boundary、metric、comparison 和 rollback rule。第二個資料齊備但仍然**完全 synthetic** 的 design，只有在所有 check 都存在時才可去到模擬的 `OWNER_APPROVED_PILOT` readiness state。

test 特意覆蓋四類失敗：沒有 human reviewer、comparison 未凍結、workflow metric 或 delayed-outcome definition 缺失，以及 action-enabled design。它不會作 network request、不會讀 key、不會發 message，更不會報告 business outcome。這正是意義所在：你可以展示自己知道真實 pilot 前要甚麼 evidence，而不是假裝已跑過一個。

程式部分會顯示 schema-like contract、immutable version、gate result 同 regression tests；而使用前仲要講清 data permission、review capacity、outcome ownership 同 stop decision。呢啲都係設計的一部分，唔係 project 尾聲先補嘅 disclaimer。

## 最常見的錯轉彎

不要因為 F1 高咗、synthetic utility 靚咗，或者 reviewer 覺得 draft 流暢，就寫「model 提升了 retention」。不要靜靜用 outcome data 揀 threshold。不要因為 dashboard 有 before／after number 就叫它 experiment；若沒有可比較的 unit、owner 和 observation rule，它只是一張圖。

較可信的 baseline 是保留現有 rule 或 manual checklist，先跑 draft-only shadow comparison；一旦 protocol 或 safety boundary 改變，就 hold candidate。NIST 的 AI RMF Core 把 governance、context、measurement 和 management 視為互相連結的工作，而不是最後打一次 compliance tick。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

## 你可以誠實放進 portfolio 的說法

> 我為一個 human-review ML workflow 建立了 local、synthetic pilot-readiness contract。它把 fixed technical evaluation、擬定的 workflow measure 和尚未觀察到的 delayed outcome 分開；沒有 owner、data boundary、frozen comparison、safety guardrail 和 rollback rule 就會 blocked。它沒有 live connection 或 external action path。

只有 repo 真有相應 evidence 才用這句。不要把匿名 role label 當真實 approval，更不要未有已授權 protocol 的量度結果前，加上 productivity、revenue 或 retention 數字。
