> offline evaluation 只能说明 candidate 在固定评估集上的表现；它不会自动证明 business outcome 已改变。中间缺少的不是更漂亮的 dashboard，而是一份有 owner、frozen comparison 和 stop rule 的授权衡量设计。

## 一个本地 demo 做得不错以后，真正少了什么？

假设你的 Renewal Triage project 已有 data contract、baseline、固定 holdout、CI check 和 rollback note。你也能解释，为什么 candidate 的 generic ranking metric 较高，却仍要被 gate 挡住。这已经比只放一个 F1 的 notebook 好得多。

但面试官会接着问：“你怎么知道它帮到 business？”

答对一半的答案是：“我会 monitor accuracy 和 reviewer acceptance。”两者都值得衡量，但都不是 business outcome。acceptance 只能反映 reviewer 是否看得懂 queue；accuracy 只能反映 model 是否对应某个 label。它们不能证明 retention、cost、quality 或 customer outcome 因为这个 workflow 而改变。

更完整的答案是：“我会先把四类证据分开，用不会改变任何下游状态的 shadow review 比较 candidate 和 baseline；只有 data owner、operations owner 和 comparison method 都获得授权后，才定义 business-outcome 问题。”下面示范怎样把这个判断做成可检查的作品证据，而且不需要连接真实系统。

## 四个数字，不能混成一句“有价值”

| 证据层 | 要问什么 | 可以支持什么 | 单靠它不能支持什么 |
| --- | --- | --- | --- |
| Hard gate | 有没有禁止字段、缺 trace 或 external-action path？ | 本地 build 应停止。 | workflow 有 business value。 |
| Model／route metric | candidate 是否正确处理固定 holdout route？ | 该 dataset 上的技术比较。 | team 变快、customer outcome 改善。 |
| Workflow metric | reviewer 能否在规定时间内按 pre-registered checklist 完成 packet？ | 受限的 operation observation。 | revenue、retention、满意度或因果效果。 |
| Delayed business outcome | 经授权的 comparison 在 outcome window 后是否看到变化？ | 有范围的 outcome finding。 | 永久或所有场景都有效。 |

Google 的 ML engineering 指引把 metric 和 instrumentation 视为系统的一部分，而不是 model 完成后才补的装饰；它也区分直接可观察的 objective 与更广泛的 system health。[Rules of Machine Learning](https://developers.google.com/machine-learning/guides/rules-of-ml) 作品集更要守住这个区别：不要把本地 proxy 写成从未衡量过的 outcome。

想象：有一个小帮手替老师把练习卡排进盒子。你能检查它有没有放对卡、老师看不看得懂标签；但不能说它让每个孩子学得更好，除非你认真比较之后真正发生的事情。

## 先画 state map，再谈 action

```text
PLANNING_ONLY
  -> SHADOW_REVIEW
  -> OWNER_APPROVED_PILOT
  -> OUTCOME_OBSERVATION
  -> HOLD 或 ROLLBACK
```

`PLANNING_ONLY` 是写清问题、metric 和边界的阶段，尚未有任何连接。`SHADOW_REVIEW` 让 candidate 在 baseline 旁边只产生 draft queue，再由人用 frozen checklist 比较；它不可以修改 account、price、message 或任何决定。

`OWNER_APPROVED_PILOT` 不是 test pass 后自己加上的标签。它需要数据和 workflow 的 owner、固定 comparison design、人工 reviewer 和 stop path。Renewal Triage 的本地 sidecar 只会**模拟**这个状态：code 检查设计是否齐备，同时始终保留 `deployable: false`、没有 connection、没有 automatic action。它不是任何真实机构的批准。

`OUTCOME_OBSERVATION` 只有在另一个已授权团队决定收集 outcome 后才开始。许多 outcome 要等数天甚至数月才知道。在 observation window 和 comparison 完成前，状态应是 `NOT_OBSERVED`，而不是“应该有正面效果”。`HOLD` 和 `ROLLBACK` 都是合理结果：有 safety breach、protocol change 或 gate fail 时，应停止 candidate，而不是用故事掩饰。

## 在看结果前，先写九格 pilot contract

在虚构 review-queue 情境中，建立一份 versioned record，至少包含以下九格：

1. **Data owner 与 boundary：** 哪一类数据可以用、哪些不能用、approval scope、retention expiry 和 deletion owner。技术上方便的数据，没有授权就不是 pilot input。
2. **Operations owner 与 human reviewer：** 谁拥有 workflow，谁能查看、hold 或拒绝 recommendation。model 不是 decision owner。
3. **Frozen comparison：** baseline version、candidate version、assignment unit、comparison strategy 和 protocol 锁定时间。看见漂亮结果后不能改 threshold、label 或 denominator。
4. **Primary workflow metric：** 定义和受限工作相符的短期衡量，例如在指定 review window 内按 checklist 完成 packet 的比例；写清 denominator 和 claim boundary。
5. **Safety guardrail：** 设定不可谈判的衡量，例如 external-action breach 必须为零，并写明 fail 时的处理方式。平均分再高也补不了不应出现的 action。
6. **Delayed outcome definition：** 写 outcome、observation window、comparison method，以及它目前为什么尚未观察到。queue ranking 本身不是 intervention；由人执行的下游 action 需要另一份 policy。
7. **Reviewer evidence：** 规定 reviewer 记录 route、reason-code reconstruction、missing evidence、checklist result 和 unresolved issue；不要和 outcome label 混在一起。
8. **Rollback decision：** 哪些情况需要 hold candidate、哪个 baseline 可以保留、谁能重开，以及需要什么新 evidence。
9. **Claim statement：** 本地设计实际示范什么、明确不示范什么，避免 README 后来变成虚构 ROI。

### 系统部分，以及使用前要说清的事

| 系统做法与检查 | 使用前要说清的事 |
| --- | --- |
| Versioned data、feature、model、prompt、baseline 和 evaluation identifiers。 | Decision owner、data owner、operations owner 和 human reviewer。 |
| Fixed cases、frozen comparison protocol、trace、failure record 和 deterministic test。 | Allowed-data boundary、retention、error cost、reviewer capacity 和 intervention authority。 |
| 一个会拒绝 connected 或 action-enabled design 的 static gate。 | Primary workflow measure、safety guardrail、delayed-outcome definition 和 stop rule。 |
| 永远 draft-only、可逆的 route。 | 对 hold、rollback 或仍缺证据的书面决定。 |

少了其中一栏，project 都会以不同方式不完整。只有 code 不能证明你有权行动；只有 business story 不能证明声称的机制被公平比较过。

## 用 Renewal Triage sidecar 练习

[Renewal Triage Lab](/zh-Hans/articles/renewal-triage-mlops) 现在有一个小型 local pilot-readiness sidecar。它的 default synthetic design 会被 blocked，因为缺少 owner、data boundary、metric、comparison 和 rollback rule。第二个资料齐备但仍然**完全 synthetic** 的 design，只有在所有 check 都存在时才可到达模拟的 `OWNER_APPROVED_PILOT` readiness state。

test 特意覆盖四类失败：没有 human reviewer、comparison 未冻结、workflow metric 或 delayed-outcome definition 缺失，以及 action-enabled design。它不会做 network request、不会读 key、不会发送 message，更不会报告 business outcome。重点就在这里：你可以展示自己知道真实 pilot 前需要什么 evidence，而不是假装已经执行过。

程序部分会显示 schema-like contract、immutable version、gate result 和 regression tests；而使用前还要说清 data permission、review capacity、outcome ownership 和 stop decision。这些都是设计的一部分，不是 project 最后才补上的 disclaimer。

## 最常见的错误转弯

不要因为 F1 变高、synthetic utility 漂亮，或 reviewer 觉得 draft 流畅，就写“model 提升 retention”。不要偷偷用 outcome data 挑 threshold。不要因为 dashboard 有 before／after number 就称为 experiment；如果没有可比较的 unit、owner 和 observation rule，它只是一张图。

更可信的 baseline 是保留现有 rule 或 manual checklist，先跑 draft-only shadow comparison；protocol 或 safety boundary 一变就 hold candidate。NIST 的 AI RMF Core 把 governance、context、measurement 和 management 看成相互连接的工作，而不是最后打一遍 compliance tick。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

## 你可以诚实放进 portfolio 的说法

> 我为一个 human-review ML workflow 建立了 local、synthetic pilot-readiness contract。它把 fixed technical evaluation、拟定的 workflow measure 和尚未观察到的 delayed outcome 分开；没有 owner、data boundary、frozen comparison、safety guardrail 和 rollback rule 就会 blocked。它没有 live connection 或 external action path。

只有 repository 真有相应 evidence 才用这段。不要把匿名 role label 当成真实 approval，也不要在已授权 protocol 产生衡量结果前，加上 productivity、revenue 或 retention 数字。
