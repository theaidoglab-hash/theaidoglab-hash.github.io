> 如果一个 eval 只能说答案听起来不错，它就无法告诉你 system 是否用了错误 source、跳过 stop rule，或把困难案例交给了没人处理的地方。

## Draft-only workflow 已足够学到关键一课

采用虚构的“退款政策草稿台”。审阅者提供净化过的问题和一小组 approved policy。系统可以写一份带 source 的内部 draft；不能承诺退款、读取账户、发送消息、修改记录。

评估目标不应只是“model 是否有帮助”，而是：在声明限制内，workflow 有没有产生 valid、source-grounded draft，或完整 handoff？目标改变后，deterministic check、human review、observability 才能协同。

## 不要只找一个神奇分数

先建立四层不需要 model judgement 的检查：

1. **Contract check**：input allowlist、JSON schema、必需 source ID、permitted route、无 prohibited field。
2. **Scenario check**：normal match、missing source、conflicting source、ambiguous wording、injected instruction、malformed output、budget exhaustion、prohibited action request。
3. **Quality check**：human reviewer 能否理解 draft、核对 citation、在不重做整件事的情况下决定下一步。
4. **Regression check**：baseline 与 candidate 运行同一冻结 case，逐 case 对比。

LLM-based judge 可以帮助有限的文字判断，例如 draft 是否清楚解释已引用 policy。它需要 written rubric、fixed example、抽样 human calibration。它不应从 final paragraph 猜测 forbidden tool call；trace 和 deterministic route check 更直接。

## Human review 是系统的一部分

先定义 reviewer 的工作。每个 case 指定 owner、收到哪些 evidence、可选什么 action。完整 handoff packet 应含 input fixture ID、approved source ID、missing fact、safe trace summary、terminal reason，以及 `KEEP_DRAFT`、`EDIT`、`REJECT`、`ESCALATE` 等选项。

让 reviewer 看到故意困难的 case：source conflict、JSON valid 但措辞弱、流畅却无 citation、因证据不足而正确被 block 的案例。这样 review 不会只奖励打磨过的 happy path。

Review 会产生资料，但它不是自动真相。记录 agreement、correction type、reviewer confidence、unresolved question。少量 reviewer 偏好不能被写成 system 已安全或 business metric 已改善。

## Observability 用来找出变化原因

Eval report 告诉你结果；**observability** 保存足够 signal，让人知道结果为什么改变。安全 trace 可保存：

```text
run_id, fixture_id, input_version, source_set_version,
prompt_version, model_configuration, parser_version,
state_transitions, allowed_tool_names, terminal_reason,
schema_result, citation_result, latency_slices, cost_proxy,
reviewer_verdict
```

默认不要保存 raw sensitive text；能用 hash、version ID、redacted summary 就不要另建私密资料库。Candidate 品质下降时，不要直接归咎 model。检查 source set、prompt version、parser repair、budget stop、cache 是否返回旧 policy；trace 让它们成为可验证假设。

## 在变更前写下 release gate

冻结 `eval-v1`，预先定 hard gate：零 invalid structured output、零没有 approved source ID 的 material claim、零 forbidden external-action route；每个 conflict、unknown、budget exhausted case 都要交给有名字的 handoff；report reviewer agreement/correction；任何 prompt/source projection/parser/model setting 改动都有 Evidence Delta 和 rollback target。

Hard gate 优先于好看的 aggregate score。一个 candidate invented refund decision，即使文风分高，也不应 release。正确 handoff 更多 edge case 的 candidate，completion rate 或许较低，反而可能更安全；两种数字都应展示。

Repository 可保留 `evals/eval-v1.json`、`rubrics/draft-quality.md`、`validators/`、`traces/schema.md`、baseline/candidate report、`CHANGE-002.md`、`review-guide.md`、`release-gate.md`。技术证据是 contract、versioned dataset、trace、comparison report、regression gate；非技术证据是 user decision、review owner、data-retention choice、failure cost、明确 non-claim。

## 边界

Desk、policy、reviewer decision、score、trace 都是虚构例子。本文没有证明真实退款 workflow、customer outcome、合规决策、production reliability、未测 input 下的安全性；它只展示在有人依赖系统前，如何让 claim 具备可检查的证据。
