> F1 分數升了，只表示同一個測試集上的分類結果變好。它不會自動告訴你誰的次序可改、實際工作是否少了重工，或較重要的錯誤有沒有增加。

## 這是一個刻意設計成合成資料的情境

想像一個完全虛構的 operations team，每星期只可覆核有限數目的續訂風險個案。某個 candidate model 的 F1 分數比透明的 rules-based baseline 高。面試官在任何人收到 candidate queue 前問：

> 「candidate 的 F1 高咗。你要看到甚麼證據，才會讓 staff 收到它排出的 queue？」

**答啱一半嘅答案：**「F1 合併了 precision 和 recall，所以 candidate 已可 release。」

這個答案知道一個 metric，卻跳過了工作上的 decision。它沒有說 reviewer 每期可以處理幾多個 case、false alert 的代價是甚麼、分數是否代表它看起來的意思、資料是否在當時已存在，或誰可以停止這個改動。

以下全部是虛構學習情境：沒有客戶資料、不會聯絡任何人、不會提出 offer 或改動帳戶，也不會聲稱 retention、收入、節省時間或 production readiness。

## 先定義 decision，才談 score

在選 metric 前，先寫一句：

> 「一位被清楚命名的 reviewer 可用這條合成 queue 決定先看哪些 case；系統不可代替對方決定，亦不可自行採取行動。」

這一句令之後每個數字都有工作。Queue 有 owner、capacity limit、baseline 和 safe stop。沒有它們，「better」只是一個好聽的形容詞。

這個例子要答的是：「reviewer 能否收到一小批可解釋、比現有 rules 更有用的 case，同時不隱藏不可接受的錯誤？」哪個 model 較準預測 label 只是其中一個證據。

## F1 高咗，先問呢六件事

### 1．Base rate：事件本身有幾罕有？

**Base rate（基準比率）** 是 model 未看任何資料前，outcome 原本出現的頻率。假設 1,000 個合成 case 裡，只有 20 個後來得到虛構的「需要覆核」label。永遠答「不需要」的系統，在關鍵地方是錯的，卻可能因為多數 case 都是 negative 而看起來很準。

所以只看 accuracy 很容易誤導，尤其是罕有事件。先記錄每個 split 裡 positive 和 negative 的數目；metric 必須連同它所描述的人口比例一起看。

### 2．Confusion matrix：錯的是哪一種錯？

**Confusion matrix（混淆矩陣）** 把結果拆成四類：

- **True positive**：queue 標記了一個 case，而它後來符合虛構的覆核 label。
- **False positive**：queue 標記了一個其實不需要覆核的 case。
- **False negative**：queue 漏掉了一個其實需要覆核的 case。
- **True negative**：queue 正確地沒有把 case 放進去。

它比單一分數有用，因為 false positive 會佔用 reviewer 時間，false negative 則可能令重要 case 沒被看見。哪種錯比較不能接受，應由這個有邊界的工作流程決定，不是由 model 自己決定。

### 3．Precision、recall 與 F1：改善的是哪個取捨？

**Precision（精確率）** 問的是：「放進 queue 的 case 裡，有幾多真係有用？」**Recall（召回率）** 問的是：「所有應該出現的 case 裡，我們捉到幾多？」**F1** 是 precision 和 recall 的調和平均數，所以其中一個很差時，F1 也會被拉低。

但只有當這個取捨吻合 workflow 時，F1 才是一個合理摘要。若 reviewer 只可看 20 個 case，一個為了捉齊所有可能 case 而送來 400 個弱 alert 的 model，並沒有令工作變容易。反過來說，若漏掉少量緊急 case 已不可接受，一條 precision 很高但 recall 太低的 queue 也不安全。把 precision 和 recall 放在 F1 旁邊，並說清為何這個平衡適合此虛構 workflow。

### 4．Calibration：分數是否真有它看起來的意思？

**Calibration（校準）** 問的是分數可否被一致地理解。在一個夠大而且可比較的合成 holdout set 裡，接近 0.70 的 case，觀察到的 outcome rate 應該大致接近 70%；若分數寫 0.70，實際卻較接近 0.20，model 就過度自信。

Calibration 不會告訴 reviewer 應怎樣做。它幫人避免把 ranking 或看似 probability 的數字當成承諾。保留 calibration plot 或 bucket table，並按對虛構 decision 有意義的維度檢查，例如 score band 和 queue position。

### 5．Threshold：誰可以入到條 queue？

**Threshold（閾值）** 把 score 轉成 queue：例如只保留某個分數以上的 case，或直接取首 20 個。它要按 reviewer capacity 和 error cost 選，不是因為 0.50 看起來很中性。

保留一張小型 capacity table：每期可看 10、20、40 個 case；對應的 precision、recall、預期 handoff 數目，以及同一 capacity 下 baseline 的結果。被命名的 reviewer 必須能以已批准的程序拒絕 queue 或改 threshold；model 從來不擁有這個決定。

### 6．Point-in-time split：model 有沒有偷看到未來？

**Point-in-time split（時點切分）** 是用每個過去 decision 當刻本來已存在的欄位去測 candidate。後來才出現的 outcome、修正過的 record、月尾總數，或 case 被覆核後才填上的欄位，不可偷偷放進 training。

這是防止 **future-data leakage（未來資料洩漏）**：model 看起來很聰明，只是因為它已看過未來的提示。做一張簡單 data-availability table：欄位、available-at timestamp、可否使用、原因。然後在同一個 held-out time window 上，比較 rules baseline 和 candidate。

## 老師的托盤，不是排行榜

想像有個小幫手，替老師把貼紙分到一個小小的「先看這些」托盤。小幫手說自己較好，因為在練習箱裡答對了更多。

先問：罕有的紅貼紙是否特別難找？托盤有沒有塞了太多普通貼紙？它說一張貼紙「很紅」時，通常真的紅嗎？老師今日只可看 20 張嗎？小幫手有沒有偷看明日答案紙的顏色？

小幫手可以提出建議；老師決定看甚麼、可以把貼紙放回去，而托盤開始令人困惑時就停止使用它。

## 由 queue 到 rollback，逐步檢查

1. **命名 decision 和 non-goal。** Reviewer 只排序虛構 queue；系統不可聯絡人、定價、批准行動或聲稱 outcome。
2. **先做最簡單 baseline。** 用透明的 rules queue 或人工 checklist 開始；candidate 出現後也保留 baseline 的 case 和結果。
3. **凍結 synthetic data contract。** 版本化虛構欄位、label、availability timestamp、point-in-time split 和排除的 future fields。
4. **公平比較 candidate 與 baseline。** 用同一批 held-out cases、capacity limit、錯誤定義、precision／recall／F1 table、calibration buckets 和代表性 failure。
5. **先行 shadow mode。** Candidate queue 只會產生建議，不會改動 live workflow。Reviewer 把它和 baseline 對比，記錄每個建議是否可理解、是否可用。
6. **用預先同意的 release gate。** 此練習要先寫好條件：不可有 data-contract failure、不可超出 capacity、不可出現不可接受的 error class，並要有 reviewer 對抽樣 case 的 sign-off。
7. **保留 rollback。** 若任何 gate 失敗，就回到已版本化的 baseline 或人工 checklist，記錄 failure，調查後才提出下一個改動。

Shadow mode 不是 launch；它只是受限比較，candidate 不能造成任何下游行動。本地的 synthetic result 仍不是 business outcome 的證據。

## 模型工作留下甚麼證據

- 一份令 future-data leakage 可見的 point-in-time data contract。
- 用 confusion matrix、precision、recall、F1、calibration 和 capacity-aware threshold 比較 baseline 與 candidate。
- 版本化 test cases、failure examples 和明確的 release／rollback gate，而不是只有 score dashboard。
- 一條可追溯連結：score、queue position、model／data version、reviewer observation 和 safe stop state。

## 交付工作留下甚麼證據

- 有 named decision owner 和有限 reviewer capacity，而不是假設自動化一定帶來影響。
- 分開 model proxy、可用 queue 和延遲才會出現的 real-world outcome。
- 清楚的 shadow-mode boundary：不聯絡客戶、不改帳戶、不提出 offer、不定價，也不做其他後果重大的行動。
- 明確 non-claim：合成資料和本地 evaluation 不證明 fairness、adoption、retention、收入或 production readiness。

## 高分最容易掩蓋的地方

不要說「F1 升了，所以創造了 business value」。不要看完 test result 才挑一個令結果好看的 threshold。不要用 candidate 最容易的一個月，比 baseline 最困難的一個月。更不要讓 score 自動派發行動。

可信而較簡單的 baseline，是一條有 capacity limit 的 rules queue 加人工 checklist。它較易解釋、較易 audit，亦給 candidate 一個真正值得贏過的比較對象。若 candidate 無法在不藏起新風險下改善虛構 reviewer workflow，就保留 baseline。

## Reviewer 可以檢查的證據

把以下放進一個清楚標明 synthetic 的 repository：

- `problem-brief.md`：user、decision、capacity、non-goal、named owner 和 stop condition。
- `data-card.md`：虛構欄位、label definition、可用 timestamp、排除的 future fields 和 limitations。
- `baseline-vs-candidate.md`：confusion matrices、precision／recall／F1、calibration buckets、capacity table 和代表性 failures。
- `threshold-decision.md`：為何選該 capacity 和 threshold、被拒絕的 alternatives，以及本應批准改動的 reviewer。
- `shadow-review-form.md`：用來記錄 usefulness、解釋質素、漏掉 case 和 handoff 的小型 rubric。
- `release-rollback-checklist.md`：gates、version identifiers、rollback target 和明確 non-claims。

這些檔案不會把 synthetic project 變成 production system；它們只讓面試官看到你能分清 model experiment 和 decision workflow。

## 一個精簡的面試答案

「F1 高咗只是一個起點，不是 release decision。我會先確認 point-in-time split，並在同一 reviewer capacity 下，用同一條 rules baseline 比較 candidate。我會看 confusion matrix、precision、recall、calibration 和代表性 failure，然後先跑 shadow mode。由被命名的 reviewer 判斷條 queue 是否可用。若資料、capacity 或安全 gate 失敗，我會保留或 rollback 到 baseline。若這是 portfolio，我會清楚標明全部是 synthetic，亦不會聲稱有 business outcome。」
