> 核心判斷：一個看似聰明的 prompt 只是一個候選設定；professional evidence 來自可重跑實驗、權限邊界和可解釋的失敗。

## Prompt play 有甚麼價值
快速試 prompt 可以探索語氣、格式和模型能力。問題出現在你只保存最好的一次輸出，然後把它當成穩定方法。沒有版本、固定 cases 和失敗紀錄，其他人無法重現你的判斷。

## 建立 experiment contract
每次實驗記錄 problem、prompt version、model/config、input class、expected behaviour、evaluation rule 和結果。一次只改一個主要變量。保存代表性錯誤，而不是只放成功例子。

## Tool permissions 必須明示
每個 tool 都要標明 read-only 或 write、可接觸的資料、外部副作用及批准者。搜尋公開資料和發送電郵不是同一風險。若 tool 可以建立、刪除、付款或傳送資料，prompt 不能代替程式權限和 human approval。

## 失敗與人工審閱
測試 ambiguous request、missing input、prompt injection、tool unavailable、partial result 和 unsafe action。為每類失敗定義 abstain、fallback 或 `NEEDS_HUMAN_REVIEW`，不要讓模型自行把不確定變成完成狀態。

## 怎樣放進 Portfolio
展示 experiment table、baseline、改動原因、failure taxonomy、permission matrix 和最終限制。面試故事可以說明你刪掉了哪個看似更靈活但風險較高的 prompt，以及怎樣用測試支持取捨。

## 下一步
下載 prompt experiment log，為一個現有 prompt 建立五個固定 cases。若每次修改後不能重跑同一組 cases，它仍然是一次性試玩，不是工程證據。
