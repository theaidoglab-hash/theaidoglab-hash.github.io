> Core judgement: a clever prompt is a candidate configuration. Professional evidence comes from repeatable experiments, permission boundaries and explainable failure.

## What prompt play is good for
Rapid prompt trials are useful for exploring tone, structure and model capability. The problem begins when you save the best output and present it as a stable method. Without versions, fixed cases and failure records, nobody can reproduce your judgement.

## Create an experiment contract
For every run, record the problem, prompt version, model/configuration, input class, expected behaviour, evaluation rule and result. Change one major variable at a time. Preserve representative failures, not only the best-looking response.

## Declare tool permissions
Every tool needs an explicit read-only or write classification, allowed data, external side effects and approval owner. Searching public information and sending an email are not equivalent risks. If a tool can create, delete, pay or transmit, a prompt cannot replace programmatic authorisation and human approval.

## Test failure and human review
Cover ambiguous requests, missing inputs, prompt injection, unavailable tools, partial results and unsafe actions. Map each class to abstention, fallback or `NEEDS_HUMAN_REVIEW`. The model must not silently turn uncertainty into a completed state.

## Make it portfolio evidence
Show the experiment table, baseline, reason for each change, failure taxonomy, permission matrix and final limitations. A useful interview story might explain why you removed a more flexible but riskier prompt and how fixed tests supported that trade-off.

## Your next move
Download the prompt experiment log and write five fixed cases for an existing prompt. If you cannot rerun the same cases after every change, it remains a one-off experiment rather than engineering evidence.
