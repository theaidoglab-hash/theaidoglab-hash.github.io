> 一張清晰的文件照片、一段語音，加上一個看似正確的回答，很容易讓人以為「多模態 AI 已經可以上線」。但真正要交付的問題不是模型能不能描述 input，而是：它是否可以讀、讀到的是什麼、哪一步要停下來，以及誰有權把結果變成行動。

## 先把 demo 收斂成一個可審核的工作

用一個**完全虛構**的案例練習：營運同事收到一張預約變更表的影像、PDF 或語音留言。系統唯一工作，是把可核對的資訊整理成草稿，交給職員覆核；它不會自行改預約、發訊息或建立客戶紀錄。

最小流程可以寫成：

`input → 類型與品質檢查 → 擷取候選欄位 → 規則檢查 → DRAFT／REVIEW／BLOCKED → 職員決定`

這條線比「我用了 vision model」重要。每一個節點都有可驗收的責任：input 是否允許處理、欄位是否有來源、結果是否完整，以及什麼情況必須交給人。模型只是其中一個可替換元件。

## 影像、文件和語音不是同一種 input

**影像**會有光線、反光、裁切、旋轉和手寫字等問題。它可能包含文字，也可能只是現場照片；不要因為看見一個畫面就推論資料可讀或可用。保留頁面或區域位置，讓 reviewer 知道某個候選欄位來自哪裡。

**文件**多了一層 layout：掃描 PDF 可能有多頁、頁首、表格、版本號和附件。OCR 或 vision extraction 可以把文字變成候選資料，卻不會自動知道哪一頁才是最新表格。檔名、檔案類型和文件版本都應是 input metadata，不是事後猜測。

**語音**不是一句已經乾淨的文字。前面還有音訊品質、語言、說話速度、背景噪音、時間點和 transcription。系統可以把「星期二下午」轉成附 timestamp 的候選內容；它不應從聲音推論身份、情緒、能力或其他不屬於任務的特徵。

三種 input 最終都可以輸出同一個 schema，例如 `requested_date`、`reference_id`、`evidence_pointer` 和 `route`。不過取得這些欄位的證據不同，因此不能只用一個「整體準確率」遮蓋所有錯誤。

## 把品質、延遲和 route 分開衡量

先建立一組合成 fixtures，不要上傳任何真實文件或錄音。可以包含清楚的打字表格、旋轉或模糊頁面、缺少關鍵欄位的附件、背景吵雜的語音，以及根本不屬於任務的 input。每個 fixture 都要寫下預期 route 和 reviewer 可以核對的 evidence。

品質至少分成三條線：

- **欄位正確性**：日期、參考編號或名稱是否符合 fixture，而不是只看整段摘要像不像；
- **route 正確性**：缺資料、低可讀性或錯誤文件有沒有走到 `REVIEW` 或 `BLOCKED`；以及
- **證據完整性**：每個重要欄位能否連回頁碼、區域或語音 timestamp。

延遲也要拆開。upload、影像前處理、轉錄、model request 和 reviewer 畫面各自花時間。先寫下可接受的等待預算，再量 p50 與 p95；沒有量到的數字就保留為假設，不要把 demo 感覺很快寫成效能證明。若語音 transcript 尚未完成，流程可以顯示「仍在處理」或直接交人，不必逼模型猜答案。

## 隱私不是把 input 交給 model 後才補救

照片、掃描文件和錄音通常比純文字更容易帶出不必要資料：背景中的人、地址、簽名、帳戶號碼或說話者的聲音。設計要從資料最小化開始：任務需要哪一頁、哪段語音、哪些欄位？不需要的就不要收、不要存，也不要放進 prompt。

作品集只能使用合成或已公開且可合法重用的素材。README 應交代 input 不可包含什麼、誰可以看原始檔、保存多久、trace 可以記錄什麼，以及示範環境沒有連接真實帳戶。redaction 或加密是可加入的控制，但不是用來合理化原本就不該收集的 input。

## fallback 的目標是保留決定，不是假裝自動化

好的 fallback 不只是「信心低就重試」。它要說清楚哪個判斷無法成立，以及下一位處理者會拿到什麼。像是 `reference_id` 被遮住、同一頁有兩個日期、語音雜訊讓關鍵詞不清楚，或文件類型不在允許清單內。系統應輸出 `REVIEW` 或 `BLOCKED`，附上頁碼、crop 或 timestamp、已擷取的候選值與不確定原因。

reviewer 可以確認、修正或拒絕草稿。這個決定需要有 case ID、input version、流程版本與 route reason，才能回看問題出在 input、extraction rule 或工作定義。不要把每次人工修正自動當成可拿去訓練的資料；先確認同意、用途和資料治理。

## 作品集要展示的不是一段漂亮輸出

一個可信的 multimodal evidence pack 可以包括：

- input taxonomy，列出支援與拒絕的影像、文件及語音種類；
- 一組 versioned synthetic fixtures，以及每個 fixture 的預期欄位、evidence pointer 與 route；
- acceptance matrix，分開欄位正確性、route、證據與 latency budget；
- privacy note，列出資料最小化、保存與 access boundary；以及
- 一張 human-handoff screen 或 trace 範例，顯示人如何理解並完成尚未完成的 case。

技術上，這證明你能設計 schema、fixtures、checks 和 trace。非技術上，它證明你知道「減少人工重新輸入」不等於取得自動修改紀錄的權限。這比用真實私人 input 做一個華麗 demo 更適合公開作品集。

## 邊界

這是學習用的 synthetic flow，不是醫療、身份驗證、監控、招聘或任何真實公司的處理建議。沒有真實 input、真實 model call、真人聲音或部署結果，就不要聲稱達到某個準確率、延遲、隱私合規或商業成效。先把 case 變得可檢查，再決定是否值得加入更多模型能力。
