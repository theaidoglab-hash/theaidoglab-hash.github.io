> 一張清晰文件相、一段語音，配上一個看似準確的回答，很容易令人以為「多模態 AI 已經做到」。交付時要回答的是：它究竟可不可以讀、讀到的是甚麼、哪一步要停低，以及誰有權把結果變成行動；model 能描述 input 只是一小部分。

## 把 demo 收窄成一個可審核的工作

用一個**完全虛構**的例子練習：營運同事收到一張預約更改表格的影像、PDF 或語音留言。系統唯一工作，是把可核對的資料整理成草稿，交給職員覆核；它不會自行改預約、發訊息或建立客戶紀錄。

最小流程可以寫成：

`input → 類型與質素檢查 → 擷取候選欄位 → 規則檢查 → DRAFT／REVIEW／BLOCKED → 職員決定`

這條線比「我用了 vision model」重要。每一個 node 都有一個可驗收的責任：input 是否容許處理、欄位是否有來源、結果是否完整、以及甚麼情況必須交人。model 只是其中一個可替換元件。

## 影像、文件和語音不是同一種 input

**影像**可能有光線、反光、裁切、旋轉和手寫字問題。它可以包含文字，亦可以只是現場相片；不要因為看見一個盒子就推論當中資料可讀或可用。保留頁面或區域位置，讓 reviewer 知道某個候選欄位從哪裏來。

**文件**多一層 layout：一份掃描 PDF 可能有多頁、頁眉、表格、版本號和附件。OCR 或 vision extraction 可以把字變成候選資料，卻不會自動知道哪一頁才是最新表格。檔名、檔案類型和文件版本都應是 input metadata，不是事後猜測。

**語音**不是一句已經乾淨的文字。先有音訊品質、語言、說話速度、背景噪音、時間點和 transcription。系統可以把「星期二下午」變成一段有 timestamp 的候選內容；它不應從聲線推論身份、情緒、能力或其他不在任務內的特徵。

三種 input 最終都可以輸出同一個 schema，例如 `requested_date`、`reference_id`、`evidence_pointer` 和 `route`。但取得這些欄位的證據不同，所以不可只用一個「整體準確率」遮蓋所有錯誤。

## 把質素、延遲和 route 分開量

用一組合成 fixtures 開始，不要上傳任何真實文件或錄音。可以有清晰打字表格、旋轉或模糊頁面、缺少關鍵欄位的附件、背景嘈雜的語音，以及根本不屬於任務的 input。每個 fixture 都寫明預期 route 和 reviewer 可以核對的 evidence。

質素至少分三條看：

- **欄位正確性**：日期、參考編號或名稱是否符合 fixture，而不是只看整段摘要像不像；
- **route 正確性**：缺資料、低可讀性或錯誤文件有沒有去 `REVIEW` 或 `BLOCKED`；以及
- **證據完整性**：每個重要欄位能否連回頁碼、區域或語音 timestamp。

延遲也要拆開。upload、影像預處理、轉錄、model request 和 reviewer 畫面各自消耗時間。寫下可接受的等待預算，並量 p50 和 p95；沒有量到的數字就留作假設，不要把 demo 感覺快寫成效能證明。若語音 transcript 未完成，流程可以顯示「仍在處理」或直接交人，毋須逼 model 猜一個答案。

## 私隱不是把 input 交給 model 後才補救

相片、掃描文件和錄音往往比純文字更容易帶出不必要資料：背景的人、地址、簽名、帳戶號碼或說話者的聲音。設計要從最小資料開始：任務需要哪一頁、哪一段聲音、哪些欄位？不需要的就不要收、不要存、不要放入 prompt。

作品集只可用合成或已公開而且可合法重用的素材。README 應寫明 input 不可包含甚麼、誰可看原始檔、保留多久、trace 可以記錄甚麼，以及示範環境沒有連接真實帳戶。redaction 或加密是可加的控制，但不是用來合理化一個本來不應收集的 input。

## fallback 的目標是保留決定，而不是假裝自動化

一個好 fallback 不只是「信心低就重試」。它要講清楚哪個判斷無法成立，以及下一個人會得到甚麼。例子：`reference_id` 被遮住、同一頁出現兩個日期、語音有噪音令關鍵詞不清楚，或文件類型不在允許清單內。系統應輸出 `REVIEW` 或 `BLOCKED`，附上頁碼、crop 或 timestamp、已擷取的候選值和不確定原因。

reviewer 可以確認、改正或拒絕草稿。這個決定要有 case ID、input version、流程版本和 route reason，方便回看問題在 input、extraction rule 還是工作定義。不要把每次人手改正自動當成可拿去訓練的資料；首先要確認同意、用途和資料管治。

## 作品集要展示的不是一段漂亮輸出

一個可信的 multimodal evidence pack 可以包括：

- input taxonomy，列出支援和拒絕的影像、文件及語音種類；
- 一組 versioned synthetic fixtures，以及每個 fixture 的預期欄位、evidence pointer 和 route；
- acceptance matrix，分開欄位正確性、route、證據和 latency budget；
- privacy note，列出資料最小化、保留和 access boundary；以及
- 一張 human-handoff screen 或 trace 範例，顯示人如何理解和完成未完成的 case。

技術上，這證明你能設計 schema、fixtures、checks 和 trace。非技術上，它證明你知道「減少人手重新輸入」不等於取得自動改紀錄的權限。這比用真實私隱 input 做一個華麗 demo 更適合公開作品集。

## 邊界

這是學習用的 synthetic flow，不是醫療、身份驗證、監控、招聘或任何真實公司的處理建議。沒有真實 input、真實 model call、真人聲音或部署結果，就不要聲稱達到某個準確率、延遲、私隱合規或商業成效。把 case 變得可檢查後，才決定是否值得加更多模型能力。
