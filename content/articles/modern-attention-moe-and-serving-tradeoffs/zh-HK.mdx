有人望住 model catalogue 說：「這個有超大 context window，又是 Mixture-of-Experts，一定快過我們的 assistant。」這個結論跳過了 workload。長 reviewer request、短 batch classification jobs，以及 peak load 下的 streaming draft，壓力都落在 serving system 的不同位置。Modern architecture terms 只有連到可觀察 workload、quality rule 和 user-facing budget，才有用。

## 這是一個工程決定

你應該能比較 small dense model、sparse expert model 和更簡單 workflow，而不是把 parameter count 當 product metric。實際要交出的，是一份 serving decision note：量了甚麼、還有甚麼未知、何時要 stop 或 handoff。

## Long context 為何改變 serving work

在 standard full attention 中，每個位置可以同 allowed context 內很多其他位置比較。Input 愈長，這些比較相關的 work 和 memory 便可能很大。較新的 attention patterns 和 implementation techniques 可以改變確實的 cost profile，但仍有取捨：哪些位置可互動、保留多少 state、有甚麼 hardware path，以及 task 是否真的需要那麼多 input。

Autoregressive model 的 serving 有兩個看得見的 phases：

- **Prefill** 在第一個 generated token 前處理 prompt 和 retrieved context；long input 會拉長 time to first result。
- **Decode** 一個 token 一個 token 產生 output，並重用如 **KV cache** 的已存 token state；long answer 會拉長 completion time 和 memory pressure。

所以「個 model 慢」是未完成的 diagnosis。高 tail latency 可以來自 queueing、long context assembly、cache pressure、output length、batch scheduling 或 service overloaded，不一定只是 model 算得慢。

## Mixture-of-Experts 改了甚麼

Dense model 每個 token 都會用到很大部分 parameters。**Mixture-of-Experts（MoE）** layer 有多個 specialised sub-networks，加上一個 router，為每個 token 只揀部分 experts。原則上，較大的 total parameter pool 可以不用每次將所有 experts 都跑完。

但「sparse」不等於免費。Router 可以令 demand 不平均；expert capacity 可以變 bottleneck；tokens 可能要在 devices 之間移動；一個紙面很有效率的 batch，若太多 tokens 揀同一 expert，P99 可以很差。Quality 亦會隨 task 和 input distribution 改變。把 MoE 當作有 routing 和 capacity 問題的 systems design，不是一個保證更快或更好的徽章。

## 測 workload，不要測 brochure

為虛構、只出 draft 的 evidence desk，先定三種 synthetic workload shapes：

| Workload | User need | Measurements | Safety check |
| --- | --- | --- | --- |
| short route | 快速 standard classification | queue delay、route quality、P50/P95/P99 | unknown category 必須 handoff |
| evidence draft | 用有限 evidence package 寫有 citation 回應 | time to first result、total time、source grounding | 無 source 就無 draft |
| long review packet | 一個嚴格有上限的長 input | context size、cache memory、completion time、review usefulness | conflict 或 budget stop 就 handoff |

每個 candidate 記 exact prompt/context version、batch setting、cache state、quantisation 或 runtime setting、output cap、quality checks，以及如知道的 hardware 或 hosted-service environment。用同一套 fixed cases 比較。Cost proxy 只在你的 measurement 支持時報告；不要將一次 local run 變成 provider-capacity claim。

## Serving levers 要有成對 guardrails

Dynamic batching 可以改善 throughput，卻可能令 urgent request 排在大 batch 後面。Prefix cache 可減少重複的 stable prompt work，但 policy text 一變便要 invalidate。KV cache 避免 decode 時重算已見 token states，代價是吃 memory 和限制 batch size。Quantisation 可減 memory demand，但改前改後都要跑同一套 quality 和 safety cases。

第一個有用 optimisation 很多時更簡單：少放不相關 context、回傳 compact schema、cap 掉沒有根據的 retries，或將不確定工作交給 reviewer。這些 control 可以同時改善 cost 和 correctness，不用一開始就押注複雜 serving stack。

## 一份 portfolio-quality serving receipt

留 `serving-decision.md`：workload assumptions、P50/P95/P99 targets、latency slices、quality 和 handoff criteria、runtime settings、observed failures，以及 rollback 或 stop rule。再加 trace fields：request class、context version、cache condition、batch condition、output size、terminal state 和安全的 reviewer destination。私人文字和 secrets 要設計上排除。

可重跑嘅 benchmark shape，加上你對 prefill、decode、cache、batching 和 expert routing 嘅解釋，會講清楚模型和 serving work 做到乜。交畀 reviewer 前，要定清楚等待上限，亦要確保 source conflict 唔會變成流暢答案；time budget 用盡時，handoff 要看得見，唔好暗中 loop。
