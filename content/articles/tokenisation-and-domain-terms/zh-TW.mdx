有人說：「這個 routing assistant 好像不懂我們的產品名稱。」最常見的反應是換模型。更值得先做的是，確認文字怎麼變成 token。像 `CX-17/Blue` 這種產品代碼，進入模型時不一定是一個完整單位；政策例外前後的標點與空格，也會改變它占用多少 context。這是可驗證的假設，不需要用更大的模型來掩蓋。

## 這一課要帶走的能力

讀完後，你應該能替一個任務做小型 token audit：記下模型實際收到的文字、使用的 context、哪些領域術語需要明確表示，以及哪些錯誤還要從別處追查。它比在作品集寫「模型懂產業術語」更能讓人檢查。

## Token 不是一個字或一個詞

Tokenizer 會把文字轉成一串稱為 **token** 的編號片段。常見方法先建立常見片段的 vocabulary，再依規則切分新文字。一個英文單字可能是一個 token，也可能是多個；空格、標點、產品代碼、emoji、中文字符或拼字錯誤，都可能形成不同組合。這些片段之後才轉成 vector，交給 Transformer 處理。

因此要記得三件事：

- Context limit、輸入成本與 latency 取決於 token 數量，不是文件字數。
- 人覺得熟悉的術語，對模型可能是一串少見的片段。
- 切分整齊不代表模型理解；切成多段也不表示模型一定無法使用。

可以把 tokenizer 想成倉儲標籤機。它把一句話轉成機器可讀的 barcode segments。切分方式會影響標籤空間與代碼在哪裡中斷，但不會讓機器因此理解退款、安全警示或客戶承諾。

## 從一個狹窄的領域案例開始

假設有一個虛構、只產生 draft 的設備退貨 desk。允許的 input 只有 category、去識別化 item code、簡短 symptom 與 policy version。團隊常用 `RMA-204`、`M12-connector`、`not safety-critical`。模型有時把 `M12` 和 `M120` 混在一起；有時在很長的 copied note 裡漏掉 `not`，把應該 review 的案件當成可以處理。

不要立刻認定是 tokenisation 的問題。先讓證據可見。建立 `token-audit.csv`：

| Input 類型 | 處理後例子 | Token 數 | 必須區分的意思 | 觀察到的行為 | 下一步 |
| --- | --- | ---: | --- | --- | --- |
| product code | `RMA-204` | 記錄 | 不可和 `RMA-240` 混淆 | route 對調 | contrast pair test |
| connector term | `M12-connector` | 記錄 | 不可當成 `M120` | 不穩定 | 加入 approved glossary field |
| risk phrase | `not safety-critical` | 記錄 | 必須 handoff，不能直接核准 | 長 note 中漏掉 | 檢查 context assembly |

案例要有真實感，但必須合法、去識別。請納入會影響判斷的變化：連字號與空格、單複數、version suffix、中英混合 label，以及相近代碼。也要保存 tokenizer version 與 model configuration，否則之後無法公平比較。

## 改善的順序比炫技重要

如果某個 domain term 會改變決定，第一個安全改善通常不是自己訓練 tokenizer。應該把 authoritative identifier 放入 structured field、用 approved catalogue 驗證，並依 identifier 取得正確 policy。欄位缺失或有歧義時，就 handoff。這是把系統從「猜這段文字是什麼」改成「使用已提供、可核對的 reference」。

你也可以比較：移除無關 copied context、在任務旁提供 glossary、比較 structured input 與 free text。這些實驗能協助區分問題是在 token budget、retrieval、prompt，還是 workflow assembly。

重訓 tokenizer、fine-tune model，或把所有術語塞進 prompt，都有成本。新 tokenizer 未必與既有模型相容；過長 glossary 會占用 context，反而遮住重要 instruction；fine-tuning 不會讓 catalogue 自動更新，更不會授權 action。如果 structured validation 已經修正錯誤，「不改模型」就是值得留下的工程決定。

## 可以放進作品集的證據

保留 token audit、少量 contrast cases、input schema 和一頁 decision note。用非技術語言說明風險：錯誤的 code 會讓 reviewer 看錯 policy；無法辨認的 code 必須 handoff，不能製造看似合理的配對。再補上技術邊界：token count 是 diagnostic signal，不是理解能力或 quality 的證明。

這些材料能讓人看見你辨識了 input representation 的風險、用近似案例檢驗假設，並選擇了有明確 owner 的 control。
