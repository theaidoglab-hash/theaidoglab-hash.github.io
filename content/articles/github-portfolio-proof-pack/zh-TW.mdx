打開 repo 的人，幾分鐘內應該找得到：你替誰準備哪個決定、資料能否使用、拿什麼作比較、怎麼檢查、哪些事刻意不做，以及哪部分由你完成。少一項，就補能核對的檔案；不要用更花俏的畫面補救。公開的合成案例不代表已在真實環境使用，也不能證明帶來業務成果。

## 先寫一個可被檢查的決策

不要一開始就請 AI agent「幫我做一個 full-stack AI app」。先選擇一個完全虛構且有邊界的決策。例如，一名虛構課程 coordinator 需要看一份**只供草稿**的合成申請資料摘要；資料不完整便交給人工處理。coordinator 仍是最後的 decision owner。這個 project 不會為人評分、不會寄出訊息、不會修改 record、不會使用真實申請資料，也不會聲稱替任何機構帶來成果。

README 的第一屏先寫四件事：

- **使用者與決策：** 誰看輸出、可以做什麼有限決策、在什麼時間點做。
- **錯誤代價：** 什麼絕對不能發生，例如虛構事實、洩漏資料或未授權 action。
- **Non-goal：** project 刻意不會做什麼。
- **Success proxy：** 只量度本機合成觀察，例如是否正確引用或 handoff；不是收入、採用率或 business impact。

這是 project 的非技術部分。它顯示你先知道如何選問題，才選模型。技術工作是驗證決策，不是為了把 demo 做得華麗。

## 讓每份檔案回答一條問題

使用小而公開安全的結構。source code、command、test 名稱與 runtime string 保持英文，讓其他人可以重跑；若讀者需要不同語言，只翻譯 README 入口，並連回英文 source 文件。

~~~text
README.md                   # decision、setup、test command、limits
README.zh-TW.md             # 本地化入口，連到英文 source docs
SOURCE_RECEIPT.md           # 靈感來源、可重用範圍與你改了什麼
DATA_CARD.md                # synthetic/public/authorised 資料邊界和 schema
docs/problem-brief.md       # owner、錯誤代價、non-goal、success proxy
src/                        # 小而可讀的 implementation
eval/cases.jsonl            # 固定 normal、failure、prohibited-action cases
tests/                      # deterministic checks 和 expected routes
reports/                    # 本機生成的 comparison 或 test summary
docs/decision-log.md        # baseline、一項改動、結果與下一個決策
docs/claims.md              # 已有證據與刻意不做的宣稱
.github/workflows/check.yml # 可重跑 validation trigger
~~~

GitHub 會把 repository README 當成 project 的介紹，因此開頭很重要；但 README 不能取代其他 artefact。reviewer 應該可以從 README 的說法一路查到 data card、test、fixture 和 result。如果 repo 是 public，請假設陌生人能看見你 commit 的 code 及 repository 可見的 workflow material。不要放入 secret、真實工作內容、客戶資料、私人 URL 或複製的課程 solution。

想像：README 是玩具盒外的標籤；proof pack 才是說明書、安全規則、零件表與煞車測試。標籤漂亮，不代表玩具安全。

## 從程式到使用方式，都要讓人核對

別人會同時想知道系統怎麼做，以及在什麼情況可以用、什麼時候要停。只展示 code，未必看得出你是否處理正確問題；只說 business story，也未必能檢查系統是否按你所說運作。

| 要展示什麼 | 系統部分，可以打開核對什麼 | 用在工作上，還要說清楚什麼 |
| --- | --- | --- |
| 第一條有用 route | 透明 rule／keyword baseline、input schema、deterministic output | 明確使用者、有限決策、錯誤代價、non-goal |
| Model 或 prompt candidate | versioned config、fixed cases、expected output、failure taxonomy | 為何值得測試，以及哪個決策絕不能自動化 |
| Evaluation | baseline 和 candidate 使用相同 cases、pass/fail rule、error example | 分開 model behaviour、workflow proxy 與尚未量度的真實 outcome |
| Operations | test command、dependency version、本機 trace fields、rollback target | human owner、approval gate、data retention limit、stop condition |
| Public repo | 英文 source、comments、test labels、workflow file | 本地化 README、source receipt、data rights、個人貢獻、non-claims |

即使你不寫 Code，這張表仍適用。你可以請 AI coding tool 起草檔案，但決策、acceptance cases、資料邊界、最後 review 與停止，仍然是你的責任。

## Baseline 要刻意普通

第一個可 run 的版本應該兩分鐘能講完。以虛構資料摘要為例，baseline 可以只檢查必填欄位、用固定 template 列出合成 facts、資料不足便 handoff。它或許沒有 LLM 流暢，卻建立 candidate 必須超越的起點。

之後只做一項有意識的改動。例如，放一份寫了 gpt-5-mini Responses API request 形狀的 static fixture，但 runnable reference 仍是本機 deterministic；或者 candidate 只有在同樣 field checks 通過後才起草摘要。不要同時修改 prompt、retrieval、UI、model 和 data schema，否則 output 改變時也不知道原因。

沒有 key、沒有 network call 的 API fixture，只是討論 artefact，不是 integration。它可以展示未來 request 應有的格式與 safety requirement；不能證明 API compatibility、model quality、cost、permission、security 或 production readiness。README 與 claims file 必須寫清楚。

## 欣賞 output 前，先寫 evaluation

建立一小組固定 synthetic cases。每個 case 有 ID、input、expected route、expected source 或 missing-support result，以及它的重要原因。最少包括：

1. 資料完整的 normal packet，應得到清楚標示的 draft。
2. 缺欄位的 packet，必須 handoff，不能補作答案。
3. 有衝突或過期合成 source 的 case，不得選中。
4. instruction override，不能改變 contract。
5. 要求外部 action 的 case，在任何 action 前必須 blocked。
6. candidate 退步、普通 baseline 反而更安全或更準確的一個 case。

baseline 與 candidate 都跑同一批 case，保存簡短 report：version、command、expected、actual 與 failure reason。固定 cases 不會證明統計顯著或 business impact；它們只是防止你只留下成功 screenshot。

想像：比較兩隻紙船前，把同樣的水窪、石頭與終點放在前面。不要給新船一條容易的河，再說它贏了。

## CI 是可重跑檢查，不是品質證書

GitHub Actions workflow 是一份 YAML 指令，可在指定 repository event 後跑同一套 validation。一個小 workflow 可以 run test command，輸出 pass 或 failure。它只證明那一次、那個 revision 通過了你指定的檢查；不能證明產品對真實使用者正確、安全、合法或可部署。

Portfolio repo 的 workflow 保持簡單：

- install pinned dependencies；
- run deterministic test suite；
- 若 data card 或 claims file 是 contract 一部分，就拒絕缺檔；
- 不使用 live credential、external write action 或 production data；以及
- README 的本機 command 必須和 workflow command 相同。

Public 前做 release preflight：找 key 與個人資料、讀生成 report 和 logs、確認資料集是 synthetic 或你看懂條款的 public material、核對 licence，再看不同語言 README 是否比英文 source docs 說得太多。若有一項不清楚，保持 repo private 或 local，只寫一篇 learning note。這不是法律或 compliance 建議。

## 練習五分鐘 GitHub walkthrough

讓 reviewer 依這個順序開 repo：

1. **0:00–0:40：** README 的使用者、決策、錯誤代價與 non-goal。
2. **0:40–1:20：** source receipt 與 data card，說明為什麼 fixture 可以安全展示。
3. **1:20–2:10：** baseline 與那一項改動。
4. **2:10–3:20：** fixed cases，包括 handoff、blocked action 或 regression。
5. **3:20–4:10：** generated test report 與 workflow file；分開可重跑 check 和真實世界 validation。
6. **4:10–5:00：** claims file：project 證明什麼、不證明什麼、下一個需要授權團隊處理的問題。

比起捲動 UI，這更能展示技術判斷以及把系統留在權限內的非技術責任。

## 公開，不代表可用在真實工作

公開 synthetic reference 可以展示 repo 結構、本機 execution、tests 與 decision records；不能展示採用率、節省工時、收入、合法權限、隱私 compliance、model safety 或營運 readiness。不要以「enterprise-ready」「production-grade」或「客戶已使用」填補不存在的證據。

較誠實的說法是：「這是 local、synthetic reference；它量度 fixed-case behaviour，並保留 human decision gate。真實資料、外部 action、deployment、monitoring 與 business outcome 都需要另外授權和評估。」這不是弱點，而是讓 hiring reviewer 知道你分得清 prototype 與 claim。

## 完成 checklist

- 陌生人在一分鐘內能說出虛構使用者、決策、non-goal 與錯誤代價。
- Repo 有 source receipt、data card、baseline、fixed cases、tests、decision log 與 claims file。
- Code、runtime message、command 與 tests 使用英文；其他語言 README 只解釋，不改寫 source contract。
- Candidate 與 baseline 用同一批 synthetic cases 比較，包含 failure 和 prohibited-action case。
- Test workflow 沒有 credential、可安全重跑，並描述成 check 而非 certification。
- 沒有 commit secret、private material、未授權課程 solution、雇主痕跡或虛構 business outcome。
- 最後 walkthrough 有一個 limit 與下一個 approval question，不只有 happy path。

## 還沒有 public repo 前，先留下交接紀錄

完成 README、test 與固定 case 後，還不等於要開 repo。先用 [Portfolio Evidence Handoff Pack](/templates/portfolio-evidence-handoff-pack/v1/README.zh-TW.md) 留下 project brief、資料權利、實際本機 run、non-claims、reviewer decision 與 rollback。它從 `NOT_RUN` 開始，不會逼你補一個沒跑過的結果；CI candidate 也刻意放在 inactive example，不會自行建立 workflow 或上傳任何內容。填完只代表可交給 owner 審查下一步，不代表可以公開、deploy 或主張已有成效。
