Reviewer 把一本很長的 policy handbook 貼進 assistant，只問一個很窄的問題。正確 exception 在第十二頁，夾在兩段講同一產品 family 的文字中間；回應卻很有信心地引用了開頭。Context window 變大，最多代表 model 收到更多字，不代表相關 evidence 一定會被選中、保留，或用在最後 route。

## 今課幫你做哪個決定

你應該能判斷一個 failure 到底需要更長 context、更好 retrieval、不同 document structure，還是安全 handoff。要留的 artefact 是一組受控的 evidence-coverage tests，不是一張一次成功的長 prompt 截圖。

## Context window 和 retrieval 做的是不同工作

**Context window** 是 model 在一次 request 中可處理的有限 input。它可以有 instructions、user request、retrieved passages、對話歷史、structured fields 和正在生成的 output tokens。較大 window 可能令你少些太早截斷文件，但也會增加 input work、cost proxy 和要處理的競爭訊息。

**Retrieval** 是另一個 system step：它在 approved collection 中搜尋，用 query 和 metadata constraints 找 candidate passages、排序，然後組一個有限 evidence package 給 model。它要將正確、最新、獲准使用的 evidence，用 reviewer 可檢查的形式送進去；文件愈多並不會自動更好。

「lost in the middle」可以當作一個實務 test pattern：同一份 evidence 放在長 context 開頭或尾端時 system 做到，放在很多干擾文字中間時卻用不到。不要把它講成所有 model、所有 workload 的定律；它是要你測 position 和 context assembly 的理由。

## 做一組 document-position evaluation

用虛構、versioned、沒有個人資料的 policy corpus。設一個 fixed question，答案由一段有名字的 passage 支持。將這段分別放在其他內容相近的 context 開頭、中間和尾端，再加一段聽落相似、但明確不是正確 policy 的近似文字。比較三條 path：

| Path | 進入 model 的內容 | 要量度甚麼 |
| --- | --- | --- |
| whole-document baseline | 有上限的完整 handbook | 正確 source ID、正確 route、input size、latency |
| metadata-first retrieval | 只取相關 policy version 和 category 的 passages | evidence recall、排除 stale versions、route |
| retrieval + compact context | top approved passages 加 task contract | grounding、missing-evidence handoff、review edit rate |

每個 case 記下 source version、query、selected passage IDs、discarded candidates、真 evidence 的位置、output、validator 結果和 reviewer judgment。Retrieval score 不能代替整個驗收：高分 passage 仍可能過期、太闊，或不適合這個決定。

## 令 assembly rule 可以被追問

Evidence package 進 model 前，先答四條問題：

1. 這個 case 可用哪個 policy version？
2. 哪些 metadata 可縮窄搜尋：category、jurisdiction、product、effective date 或 permission boundary？
3. Context budget 放得下幾段，重複或 overlap 怎樣處理？
4. 沒有 passage 支持答案，或兩段 approved passages 衝突時，會怎樣？

最終規則可以是：沒有任何一個 approved source 足以支持 route，就回 `HANDOFF`；每個 draft 都列 source ID 和 version；排除 request jurisdiction 以外的文件；retrieved passage 不可用來直接做 action。這比聲稱「有 RAG」有用得多。

## Long context 的真取捨

把整本 handbook 送入去，可能保留跨 section 的細節，減少 retrieval miss；也可能拖慢第一個回應、淹沒 task instruction，令人難以檢查哪份文字影響答案。切 chunk 切得太細，search 可能更準，卻會將一個條件同它的 exception 拆開。Top-k 太少會漏 qualifier；太多又變成一堆 noisy near matches。

沒有 universal chunk size 或 context limit。要用 evaluation set 檢查產品真會遇到的 failure shapes：互相衝突 revisions、關鍵條件放中間、很相似但 stale 的 policy、需要兩節合併才答到的問題，以及最安全 output 是「evidence 不足」的 case。

## Demo 以外值得保留的證據

留 `retrieval-coverage.md`、source manifest、position-controlled cases、query 和 metadata rules、retrieved evidence receipts 和 results table。加入一個令你改設計的 failure。也用人話說明後果：reviewer 要知道 draft 由哪個 version 支持，以及 system 何時拒絕猜。技術上亦要寫清：輸入較長不自動等於 context 較好；relevance、authority、coverage 和 traceability 要分開測。

這是一個可信的 AI-engineering 故事：你沒有將大 context window 當成 knowledge system，而是比較 baseline、定 retrieval contract，並保留人可以質疑結果的 evidence。
