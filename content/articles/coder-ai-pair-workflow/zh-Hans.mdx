在叫 coding assistant 交 diff 前，先留一张 reviewer 可以反驳的 feature brief：要改什么、哪些不做、哪些 case 必须失败，以及谁决定是否可依赖。agent 说 done，不会让这些工程判断自动交出去。

## 给会写代码的人：另一条 AI 练习路线

这篇是给 developer、analyst，或已经会在 codebase 里工作的学习者。它不是教你用一句话让 agent 生成完整产品。更有用的能力其实更窄：把一个 business need 写成可检查的改动，让 agent 提议 plan 和 implementation，但 test、review 和 release decision 留在人手。

以下 case 完全虚构，叫做 **Draft Risk Note**。想象一个小型 internal support tool 收到合成 support category 和虚构 policy flag，只能为 reviewer 生成一张本地、read-only 的 risk note。它不能发消息、修改客户记录、发 credit、call service，也不能读取真实账户。第一个改动刻意很小：当输入的 policy flag 与建议 draft route 冲突时，加入一个返回 `needs-review` 的 route。

这个练习没有真实客户、production data、API key、connector 或 business outcome claim。它要交出的，是一条证据链：清楚决定、受限 diff、fixed cases、reviewer decision 和 rollback path。

## 这篇 tutorial 明确展示什么

### Code 里看得到的东西

- 一个薄而可测的 feature slice：typed synthetic input、deterministic conflict check、draft-only output，以及明确的 `needs-review` route。
- 一个 agent-assisted workflow：先有 plan，再有受限 diff，接着有 unit／acceptance tests、本地 run record，以及可回到的 versioned rollback target。
- 把 deterministic decision path 与任何可选 language-generation layer 分开。后者只能解释已批准的结果，不能自行编造 policy state 或触发 action。

### Code 以外要交代的事

- 虚构使用者是一位 reviewer，决定一份 *draft* 是否需要多看一眼；不是让 AI 做 support、财务、法律、医疗或招聘决定。
- 成功只是一个 workflow proxy：所有固定 conflict case 到达 `needs-review`，而正常 draft case 不会坏掉。它不等于节省工时、提高满意度、收入或真实采用。
- engineer 保留 requirement、data boundary、approval、release 和 rollback 的权力。coding assistant 是有范围的 contributor，不是系统 owner。

想象：assistant 可以帮你组装玩具交通灯；但红灯代表停、要测红灯是否真的让车停下来、玩具能不能留在桌上，仍由你决定。

## 先写 acceptance brief，不要只说“把 code 写好一点”

打开 coding assistant 前，先写一段 reviewer 可以不同意的 brief。这个虚构 feature 可以是：

```text
使用者：检查合成 support draft 的 reviewer
决定：这份 draft 是否要标记为 needs-review？
输入：合成 category、proposed route、合成 policy flag
预期输出：draft-only route 加 reason code；没有 external side effect
成功 proxy：所有 fixed conflict case 到 needs-review；
             一般 matching case 保持原有 route
不做：没有 retrieval、live model call、account lookup、send 或 write
停止条件：unknown policy flag、missing field 或 unexpected route 一律 handoff
```

这比“加 safety”有用得多。它给 agent 一个有限问题，也让你有理由拒绝看起来很聪明的 implementation。未来 portfolio reviewer 也应该能验证这些边界。

## 先要 plan，还不要 diff

第一个 prompt 可以要求 agent 只交 plan，内容包括：

1. 它怎么理解 input、output、non-goal 和 stop condition；
2. 它要 inspect 或修改的确切文件；
3. 最小 implementation path，以及每个改档的理由；
4. 它会新增或更新什么 test，包括 conflict、normal case 和 missing input；
5. 哪些 assumption 要由人回答；以及
6. 确认没有独立指示前，不会读 workspace 外内容、使用 secrets、加 dependency、接 service 或做 write。

把 plan 当作 product 和 risk review 看，而不只是技术 checklist。一条三个条件的 rule，却要加 database、network call、authentication、telemetry 或新 package，已经是应该先停下来的信号。Agent 提出一种可行做法，并不等于证明那种做法合理。

## 给 agent 一份窄的 implementation contract

Plan 被接受后，给它可在 diff 里核对的限制：

```text
只实现 conflict-routing rule。
所有 source data 保持 synthetic 与 local。
不要加入 credentials、outbound requests、persistence、analytics 或 dependencies。
每个 needs-review result 都要有 reason code。
保留现在 normal case 的行为。
报告完成前先加入 fixed tests。
若有 assumption 不清楚，停止并提问，不要自行订 policy。
```

关键是“只实现”。coding assistant 很擅长填补空白；但 request 里的空白，可能变成你没有要求的架构。范围越小，scope creep 越早显现，也越容易恢复。

## 让 agent 用测试取得 PASS

先用日常语言写 acceptance cases，再把它们变成 tests。Draft Risk Note 的 case table 可以很小：

| Case | 合成输入 | 预期结果 | 绝不应出现 |
| --- | --- | --- | --- |
| Normal | proposed route 与 policy flag 一致 | 保留原有 draft route | 凭空加警告 |
| Conflict | proposed route 与 policy flag 不一致 | `needs-review` 加 reason code | 自动 override 或 send |
| Missing | 少了 category 或 policy flag | handoff 并说明 missing input | 猜答案 |
| Unknown | policy flag 不在 fixture set | handoff 并说明 unknown policy | 预设看似安全的答案 |
| Prompt-like text | 某栏文字要求 ignore contract | 当作数据处理，维持 deterministic route | 绕过 rule |

即使 agent 说 tests passed，也要由你自己跑一次。再看 test 写得对不对：只 assert 一个 truthy value 的 test，可能让错误 route 过关。留下的 evidence 应包括 command、exit result、case ID，以及任何未跑的 test。

## 像交付 review 一样看 diff

你不需要对每一行生成 code 都先假设最差，但可以从几条高价值问题开始：

- 每个 changed file 是否都在已接受的 plan 内？
- helper 有没有暗中加入 network、file-system、logging 或 package-install 行为？
- conflict rule 是否足够清楚，让另一位 developer 可以安全修改？
- test 有没有覆盖 negative path，而不是只有 happy path？
- `needs-review` 是真 route 加 reason，还是只在流畅文字里加一句？
- 未来若加 language model layer，它是否有能力改掉 decision，还是被放在 deterministic rule 后面？

一个由 AI 产生的 commit 本身还不够。保留你的 review 记录：agent 提议什么、你接受什么、你要求它改什么，以及原因。

## 第一版不要带入 secrets 或真实数据

不要因为缺 fixture，就把真实 ticket、policy 文件、database export、token 或 client detail 贴进 coding assistant。做一个小 synthetic fixture 就够了。若 task 真正需要 authorised data、external action 或 production credential，它不再适合作为这篇 tutorial 的第一个 portfolio exercise。先停止，然后在 tutorial 以外取得合适的 owner、environment、permission 和 review process。

隔离 workspace 可以减少意外 access，但不能取代判断。Prompt 里写“不要发送”不是 permission control。第一版最好的做法，是根本没有 send、write 或 call external system 的能力。

## PASS、REVISE 或 STOP，由人手 review 决定

本地 run 后，写一段很短的 reviewer note 就可以：

```text
Change：为 Draft Risk Note 加 deterministic conflict route
Evidence reviewed：plan、diff、五个 fixed cases、本地 test output
Decision：REVISE
Reason：unknown policy flag 目前会落到 normal route
Next action：加入 unknown-policy handoff test，再重跑所有 fixed cases
Release status：只限本地 learning reference；没有 external connection
Rollback：若 normal case regression，回到前一个 local rule version
```

PASS 只代表这个小改动在已写明的 synthetic environment 通过指定 cases，绝不代表 production ready。REVISE 代表 evidence 找到可修的缺口。STOP 代表问题需要真正的 decision owner、data-rights 答案、security review，或是风险更低的 first slice。知道停止，是 judgement，不是 demo 失败。

## Repo 应留下哪些东西

一个 AI-assisted coding project，应让 reviewer 找到的不只是漂亮 UI 或 model 名称。保留：

- README：虚构使用者、决定、success proxy、non-goal 和 local-only 声明；
- 已接受的 brief 和 agent plan；
- data card：fixtures 是 synthetic，还有哪些数据永远不能进 project；
- normal、conflict、missing、unknown 和 bypass attempt 的 tests；
- 有 PASS、REVISE 或 STOP 的简短 change log／reviewer note；
- 写下 command、versions、results 和已知 failure 的 run record；以及
- rollback note：哪个旧 rule 或 tag 是安全的 local fallback。

这些 evidence 让面试不只停在“你用过哪个 coding assistant？”。比较强的回答是：“我用 assistant 起草有边界的 implementation，但 acceptance cases 由我定、scope expansion 由我拒绝、negative cases 由我测，并记录什么情况要 block release。”它不会保证你得到职位，也不能证明真实 business impact；但能展示工程判断。

## 什么情况下不应使用这个 workflow

不要把这篇当成允许你把 agent 指向 production repo、customer system、live credential 或 high-impact decision 的理由。若你不能指出 human owner、不能说出可逆的 first outcome、一定要靠真实 personal data 才能运作，或回答不出错误 output 怎么被抓到，这也不是合适起点。

若你不写 code，请走另一条 [不写 Code 也能用 AI 的路线](/zh-Hans/articles/use-ai-without-writing-code)：标准一样，但你可用 no-code draft workflow 练习。想看可对照的 reference package，先读 [coding-agent review loop](/zh-Hans/articles/review-a-coding-agent-build-without-being-a-developer)。再比较 [PolicyPilot 的 deterministic 政策支持 baseline 与 RAG extension 路线](/zh-Hans/articles/enterprise-ai-portfolio-policy-pilot)、[Renewal Triage](/zh-Hans/articles/renewal-triage-mlops) 的 time-safe MLOps，并用 [portfolio-evidence rubric](/zh-Hans/articles/score-an-ai-portfolio-by-evidence-not-fluency) 检查自己的 project。准备把学习练习变成有计划的 project 时，使用 [八周 evidence sprint](/zh-Hans/articles/turn-an-ai-course-into-an-eight-week-evidence-sprint)。non-coder 的基本做法也可看 [low-code automation tutorial](/zh-Hans/articles/build-a-low-code-ai-automation)。
