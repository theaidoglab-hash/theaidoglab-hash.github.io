團隊想一個 AI system 同時做兩件事：判斷 request 應否進 standard queue，以及為 reviewer 寫一段有 citation 的解釋。「用 Transformer」還不是設計。第一件事要穩定 label；第二件事要在已提供的 evidence 上受控地寫字。知道 Transformer 裏面的 blocks 可以幫你講清差別；是否合用由 workflow contract 決定。

## 先定決定，唔好先揀 model family

先寫最小的 task statement：

> 給定 approved、已處理的 request 和 policy version，將它 route 去 `standard`、`review` 或 `out-of-scope`；如有需要，只可為 reviewer 起一份引用指定 policy 的 draft。系統不得聯絡客人或改動任何 record。

這句已經交代了 output type、boundary 和 baseline。已知 category 可以先用 deterministic rule；有足夠 versioned labels 的 routing task，才考慮 representation model；route 和 evidence 都已核實後，generative model 才可能幫 reviewer 起稿。Architecture 要贏得它的位置，不是天生應該存在。

## Transformer block 裏面做甚麼

高層來說，Transformer 接收 token representations、加入 position 的表示、反覆讓各位置交換訊息，再轉換每個位置，最後輸出結果。一個典型 block 包含：

1. **Self-attention**：讓每個 token 混合可見 context positions 的訊息。
2. **Feed-forward network** 或 MLP：在每個位置再轉換結果。
3. **Residual connections**：將較早的 signal 加回 sublayer 周圍，避免它完全消失。
4. **Normalisation**：令重複計算時的數值尺度較穩定。

這些 blocks 疊起來。最後 output head 把 representations 轉成 next-token scores、class scores、token labels 或其他 target。實作可不同，工程問題卻一樣：我們要哪種 output？怎樣驗收？

## 三種 architecture shape，三個不同問題

**Encoder-style** model 能雙向讀完整的 allowed input，產生適合 classification、search 或 ranking 的 representation。當 output 是固定 routes，又有合理的 labelled data，它可以是一個選項。

**Decoder-only** model 在 causal mask 下由左至右生成，適合起草、對話和 structured text。但它可以寫出很有自信而沒有根據的句子，所以要有 output contract、evidence check 和安全 handoff。

**Encoder-decoder** design 以 source sequence 為 input，產生 target sequence。當 source 和 output 真正是兩種不同形式，這個 sequence-to-sequence pattern 很有用；但它不會自動成為小型 routing task 的最佳選擇。

不要把它背成一張表。能寫出好看的 draft，不代表它適合 route case；能穩定分類，不代表它足以向人解釋 policy exception。

## 一個小型 architecture-choice experiment

用虛構 desk 的同一組 fixed synthetic cases，比較三條 path：

| Candidate | Product role | 要測甚麼 | 何時淘汰 |
| --- | --- | --- | --- |
| rule baseline | 已知 category routing | route、原因、維護成本 | category 經常變或 rules 衝突 |
| representation classifier | 揀固定 route | held-out route accuracy、安全的 `out-of-scope` | labels 不足或出現高風險 false approval |
| decoder draft layer | 為 reviewer 引用指定 evidence | schema、source grounding、handoff、可讀性 | invented source、不安全 route 或 review burden 太高 |

Input schema、source version、expected route、forbidden route 和 reviewer rule 要相同。不要將一個 polished generative demo 同沒有量度的 baseline 比。最有用的結論可能是：rule 仍然負責 routing，draft model 只在下游一個可 review 的位置幫手。

## Design note 應承認的取捨

更多 layers 和 parameters 不會補回沒有提供的 policy；長一點 prompt 也不是 labelled routing criteria。Decoder 可以減少 reviewer 的 blank-page effort，但增加 generation cost、output variability、prompt injection exposure 和 source verification 工作。Classifier 對 closed labels 可能較快且易量度，但新 category 一出現就可能失準。

Retrieval 也是另一回事。若要用最新 policy，按 metadata 取回 approved version，並顯示真正進入 draft 的 evidence。不要承諾 attention 內存著最新 policy，或 fine-tuning 會令一份 source 變權威。

## 能承受追問的 portfolio evidence

保留 `architecture-decision.md`：user decision、alternatives、fixed case set、evaluation measures、costs、failures 和 no-go condition。再畫一張只有任務所需元件的圖：input validation、route baseline、evidence lookup、draft layer、output validator、reviewer handoff。清楚標示哪些是 simulation，哪些 action 刻意不可用。

這讓 interviewer 或 reviewer 睇到：你能正確解釋 Transformer blocks，也知道 system architecture 是一連串有理由的 operational choices。
