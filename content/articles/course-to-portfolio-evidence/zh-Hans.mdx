把课程练习放进作品集前，记下课程提供了什么、你实际改动了什么、数据能否使用、拿什么作比较，还有故意测过哪些失败。这份记录让别人可以核对你的判断；不会把课堂练习包装成真实企业交付或业务成果。

## 完成课程后，还缺哪些证据

跟着 tutorial 做出一个画面、提交作业或拿到完成记录，可以是很好的开始。但面试官或 reviewer 通常还会问：你为什么选这个问题？哪些部分由来源提供？哪些部分是你自己改的？数据能否使用？较简单的方法表现如何？失败时系统会做什么？另一个人如何复跑？

这些问题不是要你把小练习假装成真实企业交付。相反，它们让你诚实呈现工程判断。这套做法适用于一个你已经选好的官方 tutorial、课程作业或 workshop exercise；它不评定任何供应商，也不代表任何课程、机构或雇主认可你的作品。

## 先把练习收窄成一个决定

先把原来的练习缩成一个有用户、时间点和边界的学习决定。例如，不是“做一个文件问答 bot”，而是“让一位虚构的 reviewer 在一套合成政策文件中，决定是否有足够依据起草回复，否则交回人工处理”。

写下四句：

- **用户与决定**：谁查看什么，并做出什么有限决定？
- **错误代价**：哪些错误不可接受，例如过期数据、无根据回答或未授权操作？
- **non-goal**：系统刻意不做什么？
- **可见输出**：你会留下哪一件 artefact，例如 evaluation report、data card、README 或 decision log？

这一步把课堂题目转成可被追问的工作假设，但不会把它变成真实业务成果的声明。

## 先写一张来源收据

来源收据（source receipt）不是 citation 装饰。它让人一眼分清：你学了什么、能否复用，以及你的作品从哪里开始变成自己的判断。为每个课程或 tutorial exercise 建一个 `SOURCE_RECEIPT.md`：

```text
source title: [tutorial / course / workshop exercise title]
source URL: [exact URL]
version or date: [version, release date, or "not stated"]
accessed at: [YYYY-MM-DD, timezone]
licence or terms: [exact licence / terms link, or "not stated"]
reuse boundary: [what the terms allow; link-only if unclear]
what I copied: [for example, a command pattern or high-level API sequence]
what I changed: [problem framing, synthetic data, baseline, tests, documentation]
what I did not reuse: [source solution text, proprietary data, branding, screenshots]
```

如果授权或课程条款不清楚，不要把讲义、solution code、截图或 dataset 放上公开 repository。保留网址、用自己的话重写概念，或只把独立实验留在私人学习环境，都是更稳妥的选择。这不是法律意见；你要按实际条款决定能否分享或改作。

## 数据边界要早于模型选择

最容易被忽略的问题不是 model，而是你是否有权把数据用于学习、测试、展示或发布。你的 `DATA_CARD.md` 应明确选择其中一条路：

- **合成数据**：由你编写或生成的虚构 records，标明 generator、seed、schema 和已知不真实之处。
- **已授权数据**：保留原始 licence、使用限制、是否允许衍生作业和公开展示的证据。
- **自有且已同意数据**：只有在所有相关人士明确同意该用途时才使用，并仍然最小化与去标识化。

不要把雇主、客户、同学或课程平台的非公开数据带进 project。拿不准时，改用更小的 synthetic fixture。这样会减少 demo 的“真实感”，但增加你能诚实解释的程度。

## 用一个 baseline、一项刻意改动和固定测试，代替无止境调参

把 tutorial 原本的最小方法重新实现成 **baseline**。它可以是 keyword search、rule-based router、人工模板或课程教的最简版本。然后只选择一项你有理由相信会改善指定 failure 的 **刻意改动**，例如加入 document version filter、把低置信结果交给人工，或为结构化输出加上 schema validation。

不要一次换 model、prompt、chunk size、retriever 和 UI。否则分数变好或变差时，你不知道是哪件事造成。

再建立一份不随意改动的 `eval/cases.jsonl`。至少包括：

- 一个正常、数据新鲜的 case；
- 一个没有足够依据、应交给人工的 case；
- 一个数据过期、缺字段或版本冲突的 case；
- 一个高风险或不可信输入的 case；以及
- 一个 candidate 比 baseline 更差的反例。

每个 case 都有 input、expected boundary、预期 handoff／拒答和判断准则。固定 case 不是为了假装统计显著，而是防止你只保留成功画面。若后来新增 case，保留旧版本并说明原因，不要为了掩盖 regression 重写答案。

## 每次实验留下一条可读的证据链

一份小型 experiment log 已经足够。记录日期、source version、data version、baseline、唯一改动、固定 case 结果、error taxonomy 和下一步决定。可以像这样：

```text
run: 004
baseline: keyword retrieval + human template
deliberate change: reject documents outside the active version
fixed cases: 5 passed, 1 correctly handed off
failure observed: ambiguous question still retrieved two conflicting policies
decision: keep version filter; do not add a generative answer layer yet
limit: all cases are synthetic; no customer or workflow outcome is claimed
```

真正有价值的记录包括“不采用更复杂方案”的理由。若改动没有胜过 baseline，保留 baseline 和失败证据，正好说明你不会把技术当成答案本身。

## 写好复跑指引，让判断可以被验证

README 不必很长，但要让陌生人知道最小路径。按你的实际工具为准，覆盖以下顺序：

```text
1. Read SOURCE_RECEIPT.md and DATA_CARD.md before using any files.
2. Create the pinned environment from the lockfile or requirements file.
3. Generate or download only the permitted synthetic / authorised fixture.
4. Run the baseline against eval/cases.jsonl.
5. Run the deliberate-change candidate against the same fixed cases.
6. Produce the comparison report and inspect failed or handed-off cases.
7. Do not connect write actions, personal data or external accounts.
```

加入版本、seed、config path 和预期 output path。若 project 不能完整复跑，诚实写清哪一部分受限于课程 access、API 成本或失效的第三方 service，并提供最小的 local fixture。这比假装一键部署更有用。

## 把个人贡献写成可核对的声明

在 README 加一小节“我的贡献”。不要写“我完成了整个系统”；写出你实际做的工作和未做的部分。例如：

- 我确定虚构用户决定、non-goal 和数据边界。
- 我自行编写合成 records、baseline、固定 evaluation cases 和 failure taxonomy。
- 我把 tutorial 的高层步骤改成 version filter 与 human handoff 的实验；没有复制示范 solution。
- 我没有拥有或声称拥有任何课程、队友或第三方的内容与成果。

若是小组作业，列出每位成员实际负责的 artefact，以及你可以独立讲解和复跑的部分。这不是缩小贡献，而是让信任落在准确位置。

## 用五分钟说明白这份作品

把 portfolio walkthrough 练成五分钟：

- **0:00–0:40**：说清用户决定、错误代价与 non-goal。
- **0:40–1:20**：展示来源收据和数据边界；指出什么不可复用或不可展示。
- **1:20–2:10**：走过 baseline，以及你只改了哪一个变量。
- **2:10–3:20**：展示同一组固定 cases 的比较，包括一个 failure 或 human handoff。
- **3:20–4:10**：打开复跑指引、版本和 experiment log。
- **4:10–5:00**：说明你的个人贡献、限制，以及下一个需要真实授权或人工 review 才能验证的假设。

被问到“这个 project 有没有 business impact？”时，最可靠的回答可能是：“我没有这个声明。它用合成或已授权数据测试一个有限 workflow；我把 model／system evidence 和真实 business outcome 分开。”这不是扣分，而是成熟的范围管理。

## 一张完成前检查表

- 来源收据有 URL、版本或日期、访问日期、授权／条款、复用边界、复制内容与改动内容。
- 数据被明确标为 synthetic、已授权或已同意；不含未授权的人或机构数据。
- 有可解释的 baseline、一项刻意改动和同一组固定 evaluation cases。
- README 可复跑，并说明受限部分、failure 和 non-goal。
- 个人贡献与任何小组／课程内容分开撰写。
- 五分钟答辩可展示一个正常 case 和一个失败或交给人工的 case。

这些 artefact 不保证工作、面试或收入。它们只会让对方更容易看见：当你从别人的学习材料出发时，仍然知道如何做出诚实、可检查而有边界的工程作品。
