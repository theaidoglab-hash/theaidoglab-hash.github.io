> 課程或活動值唔值得排入計劃，睇佢可唔可以喺你預先定好嘅成本內，留低一份可解釋、可重用嘅證據。

## 五個評分維度
先寫目標角色，再逐項評 0 至 2 分：角色相關性、具體輸出、實際合作／feedback、時間與金錢成本、資格與公開權利。沒有明確輸出的活動，即使內容很好，也可能只適合探索，不適合成為目前最高優先次序。

## 課程
不要只看 syllabus 有多少熱門工具。檢查有沒有 assignment、evaluation、feedback、project 和先修要求。公開教材不等於可以免費註冊；完成課程亦不等於有工作證據。預先決定你會留下哪一件 artifact，例如 evaluation report 或 reproducible notebook。

## Hackathon
選與目標工作接近的問題，事前定義自己負責的部分。活動後要在隊友同意下整理 code、tests、decision log 和個人貢獻，不能把整隊成果當成自己的。獎項可以是結果，但不應是唯一成功標準。

## Meetup 或 Demo Night
地域較窄的活動未必有大量曝光，但可用來理解公司如何描述問題。準備兩個具體問題，不要只問「有沒有工作」。記錄公開可用的職位語言，私人對話不要當成可公開引用。

## 先定義活動後的交付
報名前寫下一個活動後七日內可以完成的輸出，例如一頁 problem brief、一組 evaluation cases、整理後的 architecture note，或一段清楚界定自己貢獻的 README。若活動完結後只剩參加證書和照片，它對 portfolio 的作用通常有限。輸出亦必須尊重主辦方、隊友和資料授權；不能因為比賽結束便假設所有 code 和 dataset 都可以公開。

## 將一個真選擇寫落紙

每個機會都用同一把尺。分數唔係求職保證；佢只係喺日曆畀填滿之前，畀你睇清楚取捨。

| 維度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 角色相關 | 做嘅嘢同目標角色冇關。 | 學到一項有用嘅相鄰技能。 | 練到目標角色反覆要交嘅責任。 |
| 證據 | 得返出席紀錄。 | 可以留低筆記或半成品。 | 有權保留一份別人可檢查嘅個人貢獻。 |
| Feedback | 冇人可以 challenge 件作品。 | 可能有非正式意見。 | Reviewer、同伴或 test 會對 artefact 畀具體 feedback。 |
| 成本 | 用咗未 budget 嘅錢或時間。 | 成本可接受，但未夠清楚。 | 時間、金錢同機會成本都喺寫低咗嘅上限內。 |
| 權利同安全 | 發佈、資料或貢獻權唔清楚。 | 知道部分條件。 | Data、隊友同意同公開邊界都清楚。 |

例如一個目標係 AI application role 嘅人，拎三個虛構選擇比較：model-news webinar、週末 retrieval hackathon，同埋有 fixed evaluation assignment 嘅 course module。Webinar 嘅證據分可能低，但仍然可以用嚟定方向；hackathon 只有隊友講清楚可公開乜先可能高分；course module 如果 notebook、case 同 feedback 可以變成有邊界嘅 portfolio artefact，就可能最值得揀。重點唔係有一個放諸四海嘅排名，而係你揀咗一樣嘢，講得出原因。

## 讓個選擇喺七日內交到嘢

報名前寫低活動後七日最小要留下嘅輸出：可以係一頁 problem brief、一份清楚分開個人貢獻嘅 README，或者一組 fixed evaluation case。旁邊加一條界線：唔用機密資料、唔當隊友成果係自己、唔將學習練習寫成真實 business impact。

如果你連 artefact、owner 同留低佢嘅 permission 都講唔出，就應該扣分。咁先唔會用排滿活動日曆，拖延目標職位真正需要嘅證據。

## 停止條件
若機會與目標角色無關、沒有可帶走成果、要求不合理無薪工作、會暴露敏感資料，或時間成本擠走更直接的申請和作品工作，就應停止。下載 scorecard，比較最多三個機會後只選一個。
