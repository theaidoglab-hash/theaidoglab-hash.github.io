> 課程或活動值不值得排進計畫，取決於它能否在你預先設定的成本內，留下可解釋、可重複使用的證據。

## 五個評分面向
先寫下目標職務，再逐項評 0 至 2 分：職務相關性、具體產出、實際合作／feedback、時間與金錢成本、資格與公開權利。沒有明確產出的活動，即使內容很好，也可能只適合探索，不適合成為目前最高優先事項。

## 課程
不要只看 syllabus 有多少熱門工具。確認是否有 assignment、evaluation、feedback、project 和先修要求。公開教材不代表可以免費註冊；完成課程也不等於取得工作證據。預先決定你會留下哪一件 artifact，例如 evaluation report 或 reproducible notebook。

## Hackathon
選擇與目標工作接近的問題，事前定義自己負責的部分。活動後要在隊友同意下整理 code、tests、decision log 和個人貢獻，不能把整個團隊的成果當成自己的。獎項可以是結果，但不應是唯一的成功標準。

## Meetup 或 Demo Night
地區範圍較小的活動未必有大量曝光，但可以用來理解公司如何描述問題。準備兩個具體問題，不要只問「有沒有工作」。記錄可以公開使用的職務語言，私人對話不要當成可公開引用的內容。

## 先定義活動後的交付
報名前寫下一個活動結束後七天內可以完成的產出，例如一頁 problem brief、一組 evaluation cases、整理後的 architecture note，或一段清楚界定自己貢獻的 README。如果活動結束後只剩參加證書和照片，它對作品集的作用通常有限。產出也必須尊重主辦單位、隊友和資料授權；不能因為比賽結束，就假設所有 code 和 dataset 都可以公開。

## 把一個真實選擇寫下來

每個機會都用同一把尺。分數不是求職保證；它只是在行事曆被填滿前，讓你看清楚取捨。

| 面向 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 職務相關 | 做的事和目標職務無關。 | 學到一項有用的相鄰技能。 | 練到目標職務反覆要交付的責任。 |
| 證據 | 只留下出席紀錄。 | 可以留下筆記或半成品。 | 有權保留一份別人可以檢查的個人貢獻。 |
| Feedback | 沒有人能 challenge 作品。 | 可能有非正式意見。 | Reviewer、同儕或 test 會對 artefact 給具體 feedback。 |
| 成本 | 用掉未 budget 的錢或時間。 | 成本可接受，但仍不清楚。 | 時間、金錢與機會成本都在寫下的上限內。 |
| 權利與安全 | 發布、資料或貢獻權不清楚。 | 已知道部分條件。 | Data、隊友同意與公開邊界都清楚。 |

例如一個目標是 AI application role 的人，可以比較三個虛構選項：model-news webinar、週末 retrieval hackathon，以及有 fixed evaluation assignment 的 course module。Webinar 的證據分可能低，但仍可用來定方向；hackathon 只有在隊友說清楚能公開什麼時才可能高分；course module 若能把 notebook、case 與 feedback 變成有邊界的 portfolio artefact，就可能最值得選。重點不是有一個放諸四海的排名，而是你選了一件事，說得出原因。

## 讓選擇在七天內交出東西

報名前寫下活動結束後七天最小要留下的產出：可以是一頁 problem brief、一份清楚分開個人貢獻的 README，或一組 fixed evaluation case。旁邊加上一條邊界：不用機密資料、不把隊友成果當成自己的、不把學習練習寫成真實 business impact。

若連 artefact、owner 和保留它的 permission 都說不出來，就應該扣分。這樣才不會用排滿活動行事曆，拖延目標職務真正需要的證據。

## 停止條件
如果機會與目標職務無關、沒有可帶走的成果、要求不合理的無薪工作、會暴露敏感資料，或時間成本排擠更直接的申請和作品集工作，就應該停止。下載 scorecard，最多比較三個機會後只選一個。
