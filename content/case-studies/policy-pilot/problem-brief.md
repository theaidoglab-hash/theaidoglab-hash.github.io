# Problem brief — PolicyPilot

**狀態：僅限內部草稿｜案例：完全虛構**

## 讀者情境

假設一間中型網店的客服人員，在退貨、保養與例外規則之間反覆找資料。答錯會造成重工、升級個案和信任風險；但這個情境不是任何真實公司的描述。

## 問題陳述

如何讓客服**更快準備可核對的回覆草稿**，同時不讓模型自行作退款、改訂單或覆蓋政策的決定？

## 使用者與工作流

| 項目 | 這個案例的假設 |
| --- | --- |
| 使用者 | 經訓練的客服人員 |
| 輸入 | 一段去識別化、合成的客戶情境；不可包含真實個資 |
| 系統輸出 | 附政策引用的草稿，或「資料不足／交由人手」 |
| 最終決定者 | 客服人員或指定主管 |
| 可接受的失敗 | 拒答、要求更多資料、交接給人 |
| 不可接受的失敗 | 虛構政策、未引用便下結論、執行任何帳戶或金錢操作 |

## 作品範圍

- 僅檢索合成、版本化、帶狀態為 `approved` 的政策文件。
- 每個有結論的草稿必須帶政策 ID、版本及可閱讀引用。
- 當來源衝突、過期、缺資料或問題不在範圍時，輸出交接理由。
- 先比較 keyword retrieval baseline；加入 semantic retrieval 的前提是可量度地改善預先定義的測試集。

## 非目標

- 不處理真實客戶、訂單、付款、醫療、法律或其他高風險資料。
- 不聲稱節省成本、提升 CSAT 或減少處理時間，除非你有合法、可重複的量度證據。
- 不把 demo 變成 auto-reply、退款工具或真實政策權威來源。

## 可檢查的驗收問題

1. 每個可回答個案是否能指向適用、未過期的合成政策？
2. 缺少關鍵事實時，系統是否交接而不是猜測？
3. 測試資料與開發資料是否分開？
4. 出現失敗時，誰能停用系統、撤回文件版本和審核輸出？

## 學習者要自行決定

在開始前填寫：目標使用者、最大可接受錯誤、交接擁有人、測試集大小、release threshold，以及為何這些選擇符合你的目標職位。這些是設計假設，不是已證明的商業成果。
