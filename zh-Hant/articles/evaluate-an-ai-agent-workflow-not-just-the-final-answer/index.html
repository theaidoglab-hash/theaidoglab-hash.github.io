AI Engineer 面試：Agent 答得好，為何 workflow 仍然可能失敗？

不要只看 agent 最後答了什麼；要看它試過用什麼工具、怎麼停止、留下什麼記錄、重試會怎麼做，以及什麼時候交回給人。

一個 agent 最後寫出流暢、看似正確的句子，仍然可能沒有完成工作。它可能使用錯誤工具、重複建立同一張單、越過資料邊界、用盡預算，或把棘手個案交到沒有人看的地方。評估的對象應是 整條 workflow，不只是最後一句話。

面試官問

「如果一個 agent 會研究、呼叫工具，並把個案交給人處理，你會如何評估它，而不是只評估一次 model response？」

這張練習卡把 tool error 與 retry、tool use、終止與成本上限、可逆性、人工審核，以及 evaluation 放進同一條 workflow 練習。以下不是任何公司的題目翻譯，也不是某一個 interview loop 的預測，而是用來練習可遷移工程判斷的方法。

答對一半的答案

「我會用 LLM-as-a-judge，替最後答案評分。」

這個答案不是錯。若問題很窄，例如 final draft 有沒有引用已提供的 source，或有沒有答完整，judge 可以是一個有用的 grader。但它本身不能證明 agent 有沒有使用允許的工具、有沒有在永久錯誤後停止、有沒有留在 budget 內、有沒有避免 write action，或有沒有把模稜兩可的個案交給一個有名字的負責人。

較完整的答案，會先把工作定義為一條有狀態的 workflow，然後同時檢查最後 outcome 和它到達 outcome 的路徑。

最小而準確的心智模型

把一次 agent run 看成一個順序：

scenario → plan → tool call(s) → observation(s) → terminal state → human decision

最終回答只是 terminal state 的一部分。系統也要說清楚：它有沒有安全地完成、是否需要人、是否被阻擋、是否可重試，還是遇上不可恢復的錯誤。

層次要評估的問題可檢查的證據
Outcome使用者有沒有收到預期的 draft 或 handoff？有來源的 draft、正確 route、可理解的 reason code。
Tool pathAgent 有沒有以允許的順序呼叫允許的工具？Expected 與 observed tool sequence。
Boundaries有沒有避開禁止的 read、write、send 或 connection？Blocked-action case 與 permission log。
Recovery有沒有分辨可重試和永久錯誤？Retry 次數、terminal reason、沒有 duplicate write。
Operations有沒有留在步數、時間和成本上限內？Run duration、tool count、budget status。
Human handoff證據不足或風險上升時，有沒有交給正確的人？Handoff recipient、理由、reviewer decision。

換個畫面： 不要只因送件幫手說「包裹到了」就給它滿分。要看它有沒有走對門、沒有打開鄰居的門、地址不全時懂得停下，以及送不到時有沒有把包裹交給正確的大人。

關鍵詞，不用術語掩蓋判斷

Terminal state（終止狀態）

Terminal state 是一次 run 明確的結尾。本地示範可用的狀態包括 COMPLETE、HANDOFF、BLOCKED、RETRYABLE_ERROR 和 PERMANENT_ERROR。它們可防止 agent 把不確定變成更多不受控的步驟。

技術上，一個 state 有 reason code 和 owner 才有用。HANDOFF: source_conflict → reviewer_queue 會告訴 operator 發生了什麼和誰要決定；「我做不到」則沒有。

換個畫面： 每個遊戲都要有清楚的結局卡：「你完成了」、「問大人」、「不可以做」或「稍後再試」。沒有結局卡，遊戲可能一直玩下去。

Trace（追蹤紀錄）

Trace 是一次 run 的端到端紀錄。它應保留足以重建路徑的資料，同時避免保留不必要的敏感內容：scenario ID、input version、prompt 或 policy version、以安全粒度記錄的 tool name 與 input、tool response 或 reason code、route、terminal state、latency、cost proxy 和 reviewer result。

把 trace 當作一次 run 裡 model call、tool call、guardrail 與 handoff 的紀錄。連結的 OpenAI agent-evaluation 指引 可作 trace grading、dataset 與可重跑 eval run 的延伸閱讀；採用任何 implementation detail 前，要依你所用的產品版本重新核對。

換個畫面： 它像一條貼紙路徑，顯示小幫手去過哪些房間、試過什麼，以及在哪裡停下。

Idempotency（冪等性）

一個 action 有 idempotency，意思是重複同一請求不會造成第二次有害效果。當 agent 發了請求但在收到確認前 timeout，這個概念尤其重要。Retry 不應建立兩張 ticket、兩封訊息或兩筆付款。

在 portfolio 練習中，第一版應保持 draft-only，不能作任何外部 write。你仍可測試設計：要求 retry 重用一個虛構 action ID；如果安全地不能知道 outcome，就結束在 HANDOFF，而不是再試一次。

換個畫面： 你按兩次電梯按鈕，不應叫來兩部電梯。

Budget 與 timeout

Budget 為步數、經過時間、tool call、token 或金錢設上限。Timeout 則定義慢的 call 何時停止等候。兩者把「一直再試」變成有意識的工程決定。

面試時不要背一個萬用數字。說明你會按 user need、tool reliability、error cost 和 human-review capacity 推導上限。低風險 research draft 可用小步數 budget 後 handoff；可造成後果的 production action 需要不同 owner 和 control system。

換個畫面： 給小幫手五分鐘和三個提示去找一本書。找不到，它要問圖書館員，不是把整間圖書館翻亂。

在 happy demo 之前建立 evaluation

先做一組小型 synthetic scenario。以下的 Policy Evidence Desk 是完全虛構的：它把已核准的合成 policy snippet 變成附來源的答案草稿，不能聯絡客戶、修改 policy 或接觸真實帳戶。

不要把整條 workflow 壓成一個「agent 分數」

保留多個分開的指標：

  • Outcome correctness： Draft 是否由提供的 evidence 支持，或 handoff 是否正確？
  • Path compliance： Observed tool path 是否符合允許 route？
  • Safety compliance： 禁止的 read、write、send 和 prompt 有沒有被擋下？
  • Handoff correctness： 不確定或有後果的 case 是否交給已命名 human owner？
  • Reliability： Retry 有沒有停止、error 有沒有變成清楚 state、正常個案有沒有不必要地 handoff？
  • Efficiency： 成功 route 需要多少步、多少 latency 和多少 cost proxy？

LLM judge 可協助判斷有界的文字性質，但要以固定規則和人工覆核例子校準。喜歡流暢答案的 judge 仍可能看不出錯誤 tool path。Deterministic check 可以驗證從未請求 forbidden action，卻不能決定一份細緻的 draft 是否真正有用；兩者要刻意配合。

能經得起追問的面試答案

「我會把一次 run 定義成多於 final response。對每個 synthetic scenario，我會定義 permitted tool path、expected terminal state、handoff owner 和 prohibited action。我會保留最小 trace，包括 scenario 和 version ID、tool sequence、safety decision、latency 和 cost proxy。Outcome correctness 會和 path、safety、handoff 及 reliability 分開計分。LLM judge 只用於有界的語言準則，並用固定 cases 和 human review 校準。對 retry，我會限制嘗試次數並要求 external action 具 idempotency；如果安全地不能知道 state，我會 handoff 而不是 retry。」

再補一個誠實邊界：「這些 synthetic result 只顯示 workflow 通過了已命名 scenario set；它們不證明 production reliability、business impact、真實使用者採用、data governance，或每一種 tool 和 configuration 下的安全性。」

為何這對 AI engineer 重要

用一個固定 scenario，把 tool schema、可行路徑、trace 和 grader result 並排放；再寫清 retry／rollback 規則、誰有決策權、資料界線、錯誤代價、核准方式和不可聲稱的結果。hiring team 可以同時檢查系統行為和誰有權改變它。

NIST 的 AI RMF 把 governance、文件、人為監督和持續 risk management 視為整個 lifecycle 的工作，而非最後才加的項目。它把技術設計和組織的 roles、accountability 連起來。NIST AI RMF Core可作為這個思路的框架。你不需要聲稱已 enterprise deployment，也能展示自己明白這個連結。

要保留的 portfolio evidence

在一個清楚標明 public-safe 的 reference project 裡，保留：

  • brief.md：虛構 user、有邊界的 decision、non-goal 和 human owner。
  • scenarios.md：synthetic case、allowed tool path、expected state 和 forbidden result。
  • trace-schema.md：保留哪些欄位、刻意排除哪些欄位，以及原因。
  • results.md：outcome、path、safety、handoff、latency、cost proxy 和一個 failure。
  • decision-log.md：retry policy、budget 和 handoff threshold 為何存在。
  • release-gate.md：哪一個 regression 會阻止改動，以及如何保留 draft-only baseline。

Approval Queue reference 示範小型而 action-safe 的 DRAFT、HANDOFF 和 BLOCKED route。不寫 Code 的 permission-review guide 說明 agent 觸及真實資料前如何縮小 capability。若你會寫 code，加上 coding-partner review loop，把 agent plan 和 diff 變成可測試改動。作為 model-centric 對照，可練習 為何較高 model score 未必等於較好決策。

邊界與來源說明

這是為 AI.DOG 編寫的教學材料，不是任何公司題目的翻譯或重製，也不是現時 interview loop 的預測。情境、資料、tool、labels、capacity、輸出和 artefacts 全部是虛構；本地 synthetic evaluation 不證明 business result、production readiness 或真實風險已被解決。
