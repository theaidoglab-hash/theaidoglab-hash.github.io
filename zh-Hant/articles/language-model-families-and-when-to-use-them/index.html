選擇 language model family，不是背出越多模型名稱越好。面試官或 reviewer 真正想確認的是：你能不能把工作決策、錯誤代價，以及可驗收的證據連在一起。

從要做的決策開始

想像一個完全虛構的營運團隊，會收到簡短的設備備註。每一則備註要被分派到五個 queue 的其中一個，並產生給 reviewer 看的簡短說明。有些包含 product code，有些是中英文混用；系統絕對不能安排維修、聯絡客戶或修改任何 record。

看似單一的 request，其實包含不同工作：

  • 將文字轉成穩定的 category；
  • 從已核准案例或文件找出相近證據；
  • 依選出的證據撰寫草稿；
  • 備註附有標籤照片時讀取圖像。

不同工作不必使用同一種模型。Encoder-style model 或 embedding model 會把文字轉成 representation，適合相似度搜尋或小型分類。Decoder-style model 逐 token 產生內容，適合在 contract 下產生說明或 structured draft。Sequence-to-sequence model 讀取輸入後輸出轉換內容，較適合範圍明確的改寫與翻譯。Multimodal model 能接收多種 input，但仍需要 output contract 和人工審核邊界。

關鍵不是哪個模型「最強」，而是 workflow 的每一步是否對應真正要完成的決策。

可檢查的第一個設計

這個虛構 queue 可以先用 deterministic parser 擷取 product code、用 embedding search 找已核准案例，再套用簡單的 route rule。只有 evidence 已經選出後，才讓 generative model 寫 reviewer-facing explanation。它沒有「一個大模型處理所有事」那麼吸睛，但能讓人明確分辨問題是出在 input、retrieval、route，還是文字草稿。

Transformer 的 self-attention 會重新加權已進入 context 的 token 關係。它不會自行取得尚未提供的 policy、驗證產品紀錄，或取得外部行動的 permission。generation setting 可以調整多樣性，卻無法讓不清楚的 queue 定義變得正確。

請保留一份 model-choice record：

  • 要支援的決策，以及最後的人工 owner；
  • prototype 可使用與刻意排除的 data；
  • 不用模型時的 baseline；
  • 每一個 subtask 的候選 model family；
  • normal、ambiguous、multilingual、no-evidence 的固定案例；
  • quality、latency、cost proxy、handoff 的衡量方式；
  • 哪些情況下根本不該使用 model。

這比一張擺滿模型名稱的架構圖更能成為 portfolio evidence。reviewer 可以檢查你為什麼讓 model 寫說明，也可以看懂為什麼 routing rule 留在 model 外。

先測試邊界

用相同的 cases 比較兩個設計：一個讓 generative model 自由選擇 queue，另一個使用較窄的 workflow。不要只看句子是否自然。正確 queue 有沒有收到 case？未知的 product code 是否走到 handoff，而不是自信猜測？中英文案例是否保住 product code？草稿是否有已選 evidence 支持？

常見問題是把 chat model 當成萬用 classifier，然後把流暢的理由誤認為正確；另一種是把 embedding 的相似度當成 policy relevance。若 label set 很小且穩定，error cost 也清楚，deterministic rule 或傳統 classifier 可能才是誠實的 baseline。照片如果只是選用 input，就不該讓每個純文字 case 都依賴 vision。

你留下的是判斷證據

技術證據是 task decomposition、model contract、test set 和 comparison report。非技術證據是 user decision、data boundary、error cost、human handoff，以及保留簡單步驟的理由。它們不代表 production ready 或有業務成果；它們顯示你能在擴大 demo 前做出可被追問的工程選擇。

接著可閱讀：Transformer、generation 與 adaptation 的取捨、調參前先理解 neural model 如何學習，以及把 request 轉成可接受的改動。

邊界

這是 AI.DOG 的教學案例。團隊、input、queue、指標與結果均為示範，不建議特定 provider 或 model，也沒有聲稱本地 prototype 處理過真實客戶資料或改善過真實 business outcome。
