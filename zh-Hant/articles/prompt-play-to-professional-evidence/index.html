一條 prompt 曾經產生一次有用答案，最多證明它值得試。真正要看的是：reviewer 能否知道哪個改動有效、它會在哪裡失敗，以及何時一定要停止。

Prompt play 有什麼價值

快速嘗試 prompt 可以探索語氣、格式和模型能力。問題出現在你只保存最好的一次輸出，然後把它當成穩定方法。沒有版本、固定 cases 和失敗紀錄，其他人無法重現你的判斷。

建立 experiment contract

每次實驗記錄 problem、prompt version、model/config、input class、expected behaviour、evaluation rule 和結果。一次只改一個主要變數。保存代表性錯誤，而不是只放成功案例。

Tool permissions 必須明確

每個 tool 都要標示 read-only 或 write、可接觸的資料、外部副作用及核准者。搜尋公開資料和寄送電子郵件不是同一種風險。如果 tool 可以建立、刪除、付款或傳送資料，prompt 不能取代程式權限和 human approval。

失敗與人工審核

測試 ambiguous request、missing input、prompt injection、tool unavailable、partial result 和 unsafe action。為每類失敗定義 abstain、fallback 或 NEEDS_HUMAN_REVIEW，不要讓模型自行把不確定狀態變成完成。

如何放進作品集

展示 experiment table、baseline、改動原因、failure taxonomy、permission matrix 和最終限制。面試故事可以說明你刪除了哪個看似更靈活、但風險較高的 prompt，以及如何用測試支持這項取捨。

一次只改一件事

用完全虛構的 Intake Draft Desk 練習。它收到一段合成 request，只能替 reviewer 寫有標記的 draft；不能發送、更新資料，也不能離開提供的 fixture set 搜尋。先用 rule 擋住沒有 request type 的 input，再逐次比較一個 prompt 改動。

版本這次刻意只改了什麼固定留下的證據執行後可作的決定
v1純 rule route 加固定 draft template。五個 case 的預期 route label。保留作安全 baseline。
v2加一條抽取 request type 的 prompt。同一組五個 label，加完整 prompt text。只有改善指定 case、又不影響 blocked case 才保留。
v3加入 retrieved context。v2 case，再加一個過期與一個衝突 source。若缺資料或舊資料變成自信 draft，就拒絕。

不要只比較文字漂不漂亮。並排看 route、引用哪個 fixture ID、terminal status 與 reviewer 花多少工夫。若 model、prompt、input shape 和 grader 一次都變了，之後無法說明是哪一項造成差異。

五個 case 已足夠看見邊界

一開始不用做一大堆 benchmark。寫一組小型 answer key，讓 workflow 顯示自己會如何收手。

這張表同時分開兩份證據。技術記錄包含 version、input class、expected state、trace 與 test result；交付記錄要說清誰能 review draft、為何需要 handoff，以及系統永遠拿不到哪種 action 權限。

有時最好的改動是不使用 model

若 deterministic rule 已準確擋住所有 missing-field 與禁止 action 的 case，不要只因 model 可以寫得較順就換掉它。保留 rule 在邊界，只在 model 真能改善的小段 draft 使用它。這個決定，比每一層都加入 agent 更有說服力。
