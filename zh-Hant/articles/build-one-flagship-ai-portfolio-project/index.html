作品集證據

先做好一個主力案例：用六格整理可核對的 AI 作品集

用一個合成或公開資料案例，逐格留下檔案、檢查方法與不能聲稱的結果；第二個 project 只在它補到另一種決策時才值得開始。

一張六格作品地圖：每格都有可開啟的 artefact、檢查方法與不能聲稱的結果，再加一段五分鐘 walkthrough。
時間與練習範圍

閱讀與複核: 5–10 分鐘 按本語言版本的內容長度估算。

整理與自我檢查: 45–60 分鐘 建議完成本文的證據任務。

一個主力案例不必很大。它只要讓陌生人打開幾份檔案後，看得出你想替誰處理哪個小決策、如何檢查，以及你沒有把本機練習說成真實成果。

主力案例不是功能最多的那個

作品集常見的問題不是能力不夠，而是同時開始三、四個半完成的 project：一個 RAG chat、一次模型微調、一個 agent，再加上一個好看的介面。每個都能 demo 幾分鐘，卻沒有人能順著檔案追問你的取捨。

主力案例要反過來做。只選一個有限情境，再把六項原本散在腦中的資訊寫下來。它不必碰真實客戶、雇主資料或外部帳戶；合成資料或條款清楚的公開資料，已足夠做學習版本。重點不是把它說成企業系統，而是讓 reviewer 能沿著同一條線看見你的判斷。

如果還沒有選題，先用 Portfolio Evidence Planner 寫出一位使用者、一個小決策、資料邊界與一件刻意不做的事。不要先從 model、framework 或職稱倒推題目。

先用一句話篩掉不值得做的題目

把候選題目寫成：「一位 __ 在 __ 時，要根據 __ 決定 __；如果資料不足、過期或超出權限，就 __。」

例如，不是「我要做一個 AI 文件助理」，而是「一位虛構 reviewer 收到一筆資料更新時，要決定能否準備一份附來源的草稿；來源衝突或缺欄位，就停在交給人處理。」這一句已逼你選 owner、時間點、輸入、停止點與錯誤後果。

以下情況先別選作主力案例：一定要靠未獲准的資料才有意義、只能用漂亮輸出展示，或你連一種可能失敗的情境都想不到。這些不是「再加一個 agent」能補救的問題。

六格：每格都留下檔案、檢查方法與不能聲稱的結果

這六格不是要你堆六份文件。每一格都對應一條合理追問。你可以先寫一頁短 Markdown；有實際改動時，再把它長成 code、測試或紀錄。

格留下什麼 artefact別人怎麼檢查這格不能聲稱什麼
01 · 小決策docs/problem-brief.md，寫使用者、決策時間、錯誤代價、owner 與 non-goal。讀者能用一句話說出工具替誰做哪個有限決策，也知道誰保留最後決定權。不代表已有真實需求、客戶、授權或採用。
02 · 資料邊界docs/data-receipt.md、schema 與一小份 synthetic 或公開 fixture。能分辨資料來自哪裡、哪些欄位可用、哪些必須排除、資料是哪個版本。不代表你有真實資料存取權、隱私核准或仍然新鮮的 live data。
03 · 簡單起點src/baseline.* 與 docs/baseline-and-change.md，記下最簡單做法與一次刻意改動。同一個 input 能走 baseline 與 candidate；讀者能指出改了什麼、為何改。不代表 candidate 在真實工作中較好，也不代表較複雜就更有價值。
04 · 固定情境eval/cases.*、預期 route 與 failure log。至少能看到正常、資料不足、過期或衝突、越界要求與 regression case 的預期處理。不代表統計 benchmark、完整安全測試或任何認證。
05 · 停止與回退docs/reviewer-decision.md 與 docs/rollback.md，寫 KEEP、REVISE 或 STOP 的條件。別人能知道哪個失敗會擋住改動、誰做決定，以及怎麼回到前一個可用方法。不代表已取得 release、部署、資安或合規核准。
06 · 交代給下一個人README.md、最小 run command、docs/five-minute-walkthrough.md 與 claims note。一位陌生人能找到入口、理解本機結果從何而來，並聽你說清一個 failure。不代表公開 repository 已存在、每行 code 都由你獨自寫成，或 project 能保證求職結果。

第 03 格特別重要。沒有 baseline 時，你只是在展示「某個組合可以跑」。有了同一批 input 的簡單比較，才可以討論新元件到底補了哪種 failure，又帶來什麼成本或新風險。

第 04 格也別只放成功 screenshot。固定情境的價值在於你改 prompt、retrieval、rule 或 model 後，仍能看出舊問題是否回來。一次本機 pass 只表示那次本機檢查；不是 live system 的成績單。

先讓一格站得住，再開下一格

這張表最容易被誤解成「今晚要補齊所有文件」。更好的做法是讓每次工作都把一格從空白變成能打開的東西：

  1. 先完成第 01 與 02 格，否則你不知道自己能用什麼資料、不能做什麼。
  2. 做出第 03 與 04 格的最小版本；保留一個 baseline、一項改動與同一批 cases。
  3. 最後補第 05 與 06 格，讓改動有人能 review，也讓你幾週後仍說得回來。

想看一個從舊快照排人工佇列的例子，可讀 Renewal Triage。它刻意把模型分數、佇列行為與真實挽留結果分開。想從草稿流程開始，可在 Build Lab 選一個本機練習；內容本身不會替你連接帳戶、資料或真實工作流程。

第二個 project 什麼時候才有理由開始

第二個 project 不是第一個畫面看膩了就開始。至少先問三個問題：

  • 它有沒有另一個決策？ 把同一個 FAQ 換 prompt、換 model 或換介面，不算另一個 case。從「能否草擬回覆」轉到「有限 capacity 下先 review 哪一筆」，才是不同決策。
  • 它有沒有另一種失敗方式？ 例如 retrieval project 要處理來源、版本與無根據回答；時間序列或 queue project 要處理資料可用時間、capacity 與 threshold。只換主題色彩不會增加你能展示的判斷。
  • 第一個是否已有一輪完整回應？ 六格每格至少有一件能打開的東西，而且你已根據同一批 cases 接受、修改或放棄過一次改動，才值得把注意力轉走。

PolicyPilot 與 Renewal Triage 可以是一對好對照，不是因為名稱較大，而是它們的問題不同：前者著重來源支持的草稿與交人；後者著重時間安全的資料、排序與 reviewer capacity。你可從 PolicyPilot 讀另一種有限 case，但別把兩者混成一句「我做過 enterprise AI」。

把六格變成面試時說得出的路線

開始前可參考 Portfolio Proof Pack 的文件結構，再把每一格連到一個檔案。接著打開 Interview Lab，選一題與你案例最接近的題目。回答時不用重複 README；按這個順序說就好：哪個決策、最簡單做法、哪個 case 逼你修改、怎麼停下，以及那次本機練習仍不知道什麼。

想先檢查自己漏了什麼，也可對照 作品集 evidence review。它能幫你找下一個缺口；這篇則幫你避免把缺口分散到幾個半完成 project。

這份地圖的邊界

這是一份學習用架構，不會建立 GitHub repository、不會公開資料、不會替你執行 model call，也不會讓本機 fixture 變成真實業務結果。使用雇主、客戶、同學或任何個人資料前，仍要由有權的人確認用途、權限、保存與公開範圍。

一個主力案例的價值，是讓別人不必相信你說「我做過 AI」，也能沿著你留下的六格，看到你在哪裡縮小問題、如何檢查、何時停止，以及哪些問題仍未有答案。
