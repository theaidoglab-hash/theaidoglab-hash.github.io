面試官問：一個團隊想讓 internal assistant 更穩定地輸出固定摘要格式，但可用 training memory 不多，domain reviewer 每週也只能看有限樣本。你會在 prompt、retrieval、adapter、量化 adapter 或 full fine-tune 之間怎樣選？

答對一半的答案：資料不多就用 LoRA；GPU 不夠就用 QLoRA，效果不夠才 full fine-tune。

這個答案知道幾種方法，卻把 resource constraint 當成唯一決定。Adaptation 先要問失敗模式是否穩定、可用資料是否真的代表目標工作、較簡單 baseline 是否已被公平測過。Prompt 或 output validator 能修正介面或控制問題；retrieval 能補外部知識；adapter 只訓練一小部分可插入參數；LoRA 用低秩更新代表那份改動；QLoRA 常見做法是以量化 base 減少記憶體壓力，再訓練 adapter；full fine-tune 則改動更大範圍的 model weights。它們不是由「最潮」排到「最強」，而是有不同 memory、資料、回歸與可驗證成本。

先把兩份 budget 寫出來

Memory budget 不只是 GPU 顯示多少 GB。它包括 base model、optimizer states、gradient、activation、batch、sequence length、checkpoint、data pipeline 與保留空間。可以把 batch 縮到能跑，但若 sequence 或 batch 讓訓練噪音太大、迭代太慢，這未必是可交付候選。Eval budget 也不只是算一次分數：它包括 frozen baseline、held-out fixed cases、要分開看的 critical slices、reviewer 可檢查樣本數、run time，以及出現 regression 時停下或 rollback 的時間。

先寫一份 failure inventory。例子：格式欄位常漏、數值只在舊資料出錯、長文件才偏題，或 reviewer 說「像錯」卻未能指出 acceptance rule。每種 failure 會導向不同第一步。若 schema validator 已可確定偵測與修復漏欄位，training 可能只是把可解釋問題藏進 weights；若 retrieval source 會變，把知識背進 adapter 又可能讓更新更難。只有當同一行為在資料裡穩定、baseline 已盡力、而你有可保留 eval case，才值得比較 adaptation 候選。

想像校服要改合身。Prompt 或 validator 像先扣好鈕、量好尺寸；retrieval 像帶回最新尺碼表；adapter 像加一塊可拆小布，改動有限也易換回；full fine-tune 像把整件衣服拆開重縫。若只是少扣一粒鈕就拆整件衣，花的布與工夫多，還可能弄壞本來合身的地方。先知道哪一處不合，才知應貼布還是重縫。

一個能被 review 的選擇順序

  1. 固定 target behaviour、non-goal 與 synthetic／已獲准資料邊界；把 baseline prompt、retrieval、validator 與 model version 鎖住。
  2. 做 2–3 個較省的候選：只修 contract、改善 retrieval／data、或小 adapter。每個候選寫 memory estimate、可跑 batch／sequence、資料要求與預期風險。
  3. 用同一 held-out set 跑格式、事實、長度、語言與關鍵 workflow slices；先看 failure examples，再看總分。
  4. 通過 gate 才增加訓練範圍。若 reviewer budget 不足以判定 regression，暫停升級，不要把不確定當成提升。
  5. 保存 candidate、config、data receipt、eval result 與拒絕理由，讓下一個人知道不是因為「感覺」選方法。

答案的盲點通常在哪裡

「QLoRA 較省 memory」可以是對的，卻不回答你在優化什麼。它沒說哪些 layers、資料格式、sequence length、eval slices 與回退方式讓風險可控。相反，full fine-tune 過不了 critical slice，並不代表要盲目再跑更多 epoch；可能要回到 label、prompt、retrieval 或 acceptance rule。好的 engineer 會把選擇寫成可否決實驗，而不是把 memory limit 變成技術炫耀。

可以親手做出來給人核對的東西

建立 adaptation-budget-decision：

  • docs/failure-inventory.md：虛構 target behaviour、baseline、non-goal 與可觀察 failure pattern。
  • config/candidates.yaml：prompt-only、retrieval change、adapter 與 full-tune 候選的 memory／time estimate。
  • fixtures/held-out-cases.jsonl：格式、長度、語言、長 context 與關鍵錯誤的固定 cases。
  • evidence/eval-by-slice.md：每個候選的 sample、總分、slice result、review decision 與停止條件。
  • tests/no-regression-gate.test.ts：任何 critical slice 低於 baseline 時 fail。

要展示的不是「我成功 fine-tune」，而是「我知道何時不應 fine-tune，並留下足夠證據讓人重複這個判斷」。
