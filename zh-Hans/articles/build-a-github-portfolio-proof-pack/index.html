打开 repo 的人，几分钟内应该找得到：你为谁准备哪个决定、数据能否使用、拿什么作比较、怎样检查、哪些事刻意不做，以及哪部分由你完成。少一项，就补能核对的文件；不要用更花哨的画面补救。公开的合成案例不代表已在真实环境使用，也不能证明带来业务成果。

先写一个可检查的决策

不要一开始就让 AI agent“帮我做一个 full-stack AI app”。先选择一个完全虚构且有边界的决策。例如，一名虚构课程 coordinator 需要看一份只供草稿的合成申请资料摘要；资料不完整便交给人工处理。coordinator 仍是最后的 decision owner。这个 project 不会为人评分、不会发送讯息、不会修改 record、不会使用真实申请资料，也不会声称替任何机构带来成果。

README 第一屏先写四件事：

  • 用户与决策： 谁看输出、可以做什么有限决策、在什么时间点做。
  • 错误代价： 什么绝对不能发生，例如虚构事实、泄露数据或未授权 action。
  • Non-goal： project 刻意不做什么。
  • Success proxy： 只衡量本地合成观察，例如是否正确引用或 handoff；不是收入、采用率或 business impact。

这是 project 的非技术部分。它说明你先知道如何选问题，才选模型。技术工作是验证决策，不是为了把 demo 做得更华丽。

让每份文件回答一条问题

使用小而公开安全的结构。source code、command、test 名称和 runtime string 保持英文，让其他人可以重跑；若读者需要不同语言，只翻译 README 入口，并链接回英文 source 文件。

~~~text

README.md # decision、setup、test command、limits

README.zh-Hans.md # 本地化入口，链接到英文 source docs

SOURCE_RECEIPT.md # 灵感来源、可复用范围和你改了什么

DATA_CARD.md # synthetic/public/authorised 数据边界和 schema

docs/problem-brief.md # owner、错误代价、non-goal、success proxy

src/ # 小而可读的 implementation

eval/cases.jsonl # 固定 normal、failure、prohibited-action cases

tests/ # deterministic checks 和 expected routes

reports/ # 本地生成的 comparison 或 test summary

docs/decision-log.md # baseline、一项改动、结果和下一个决策

docs/claims.md # 已有证据和刻意不做的宣称

.github/workflows/check.yml # 可重复 validation trigger

~~~

GitHub 会把 repository README 当作 project 的介绍，因此开头很重要；但 README 不能取代其他 artefact。reviewer 应该可以从 README 的说法一路查到 data card、test、fixture 和 result。如果 repo 是 public，请假设陌生人能看见你 commit 的 code 及 repository 可见的 workflow material。不要放入 secret、真实工作内容、客户数据、私人 URL 或复制的课程 solution。

想象：README 是玩具盒外的标签；proof pack 才是说明书、安全规则、零件表和刹车测试。标签漂亮，不代表玩具安全。

从程序到使用方式，都要让人核对

别人会同时想知道系统怎样做，以及在什么情况可以用、什么时候要停。只展示 code，未必看得出你是否处理了正确问题；只说 business story，也未必能检查系统是否按你所说运作。

要展示什么系统部分，可以打开核对什么用在工作上，还要说清什么
第一条有用 route透明 rule／keyword baseline、input schema、deterministic output明确用户、有限决策、错误代价、non-goal
Model 或 prompt candidateversioned config、fixed cases、expected output、failure taxonomy为什么值得测试，以及哪个决策绝不能自动化

即使你不写 Code，这张表仍适用。你可以让 AI coding tool 起草文件，但决策、acceptance cases、数据边界、最后 review 和停止，仍然是你的责任。

Baseline 要刻意普通

第一个可 run 版本应该两分钟能讲完。以虚构资料摘要为例，baseline 可以只检查必填字段、用固定 template 列出合成 facts、资料不足便 handoff。它可能没有 LLM 流畅，却建立 candidate 必须超过的起点。

之后只做一项有意识的改动。例如，放一份写了 gpt-5-mini Responses API request 形状的 static fixture，但 runnable reference 仍是本地 deterministic；或者 candidate 只有在同样 field checks 通过后才起草摘要。不要同时修改 prompt、retrieval、UI、model 和 data schema，否则 output 改变时也不知道原因。

没有 key、没有 network call 的 API fixture，只是讨论 artefact，不是 integration。它可以展示未来 request 应有的格式和 safety requirement；不能证明 API compatibility、model quality、cost、permission、security 或 production readiness。README 和 claims file 必须写清楚。

欣赏 output 前，先写 evaluation

建立一小组固定 synthetic cases。每个 case 有 ID、input、expected route、expected source 或 missing-support result，以及它的重要原因。最少包括：

  1. 资料完整的 normal packet，应得到清楚标示的 draft。
  2. 缺字段的 packet，必须 handoff，不能补作答案。
  3. 有冲突或过期合成 source 的 case，不得选中。
  4. instruction override，不能改变 contract。
  5. 要求外部 action 的 case，在任何 action 前必须 blocked。
  6. candidate 退步、普通 baseline 反而更安全或更准确的一个 case。

baseline 和 candidate 都跑同一批 case，保存简短 report：version、command、expected、actual 和 failure reason。固定 cases 不会证明统计显著或 business impact；它们只是防止你只留下成功 screenshot。

想象：比较两只纸船前，把同样的水坑、石头和终点放在前面。不要给新船一条容易的河，再说它赢了。

CI 是可重复检查，不是品质证书

GitHub Actions workflow 是一份 YAML 指令，可在指定 repository event 后跑同一套 validation。一个小 workflow 可以 run test command，输出 pass 或 failure。它只证明那一次、那个 revision 通过了你指定的检查；不能证明产品对真实用户正确、安全、合法或可部署。

Portfolio repo 的 workflow 保持简单：

  • install pinned dependencies；
  • run deterministic test suite；
  • 若 data card 或 claims file 是 contract 一部分，就拒绝缺文件；
  • 不使用 live credential、external write action 或 production data；以及
  • README 的本地 command 必须和 workflow command 相同。

Public 前做 release preflight：找 key 和个人数据、读生成 report 和 logs、确认数据集是 synthetic 或你读懂条款的 public material、核对 licence，再看不同语言 README 是否比英文 source docs 说得过火。若有一项不清楚，保持 repo private 或 local，只写一篇 learning note。这不是法律或 compliance 建议。

练习五分钟 GitHub walkthrough

让 reviewer 按这个顺序打开 repo：

  1. 0:00–0:40： README 的用户、决策、错误代价和 non-goal。
  2. 0:40–1:20： source receipt 和 data card，说明为什么 fixture 可以安全展示。
  3. 1:20–2:10： baseline 和那一项改动。
  4. 2:10–3:20： fixed cases，包括 handoff、blocked action 或 regression。
  5. 3:20–4:10： generated test report 和 workflow file；分开可重复 check 和真实世界 validation。
  6. 4:10–5:00： claims file：project 证明什么、不证明什么、下一个需要授权团队处理的问题。

比起滚动 UI，这更能展示技术判断以及把系统留在权限内的非技术责任。

公开，不代表能用在真实工作

公开 synthetic reference 可以展示 repo 结构、本地 execution、tests 和 decision records；不能展示采用率、节省工时、收入、合法权限、隐私 compliance、model safety 或运营 readiness。不要以“enterprise-ready”“production-grade”或“客户已使用”填补不存在的证据。

更诚实的说法是：“这是 local、synthetic reference；它衡量 fixed-case behaviour，并保留 human decision gate。真实数据、外部 action、deployment、monitoring 和 business outcome 都需要另外授权和评估。”这不是弱点，而是让 hiring reviewer 知道你分得清 prototype 和 claim。

完成 checklist

  • 陌生人在一分钟内能说出虚构用户、决策、non-goal 和错误代价。
  • Repo 有 source receipt、data card、baseline、fixed cases、tests、decision log 和 claims file。
  • Code、runtime message、command 和 tests 使用英文；其他语言 README 只解释，不改写 source contract。
  • Candidate 与 baseline 用同一批 synthetic cases 比较，包含 failure 和 prohibited-action case。
  • Test workflow 没有 credential、可安全重复运行，并描述为 check 而非 certification。
  • 没有 commit secret、private material、未授权课程 solution、雇主痕迹或虚构 business outcome。
  • 最后 walkthrough 有一个 limit 和下一个 approval question，不只有 happy path。

还没有 public repo 前，先留下交接记录

完成 README、test 和固定 case 后，还不等于要开 repo。先用 Portfolio Evidence Handoff Pack 留下 project brief、数据权利、实际本机 run、non-claims、reviewer decision 和 rollback。它从 NOT_RUN 开始，不会逼你补一个没有跑过的结果；CI candidate 也刻意放在 inactive example，不会自行建立 workflow 或上传任何内容。填完只代表可交给 owner 审查下一步，不代表可以公开、deploy 或主张已有成效。
